## Rationale

- `src/index.js` tool lookup: the agent is its own scope key, so `ctx.skills.list` resolves the layered registry exactly as that agent's composition sees it.
- `src/index.js` user-explicit invocation (`agent/pre-step`): a claimed user message whose first line starts with `/<name>` naming a user-invocable skill is a deterministic load gesture. The rendered body is appended as injected instructions after every other injection (background first, the material the model must act on last, closest to its answer); this listener registers before the catalog listener so the waterfall hands it the catalog-bearing list to extend.
- `src/index.js` same listener, trust boundary: only `source.kind === 'user'` messages are scanned so external text cannot forge the gesture; unknown names and user-disabled skills stay plain prose (checked on the loaded definition, the single lookup that produces what is injected); the command registry is a separate namespace resolved client-side. This is the only entry point for `disable-model-invocation` skills; the catalog and the `skill` tool never see them.
- `src/index.js` catalog listener: registered after the tool so reverse teardown removes guidance first. It compares against the definition this plugin registered (exact identity), not a lookup by name, because `register()` files into the calling context's scope: a plugin mounted in an agent preset registers for that agent alone and an unscoped lookup finds nothing, and a scoped shadow merely named `skill` must not inherit the catalog.
- `src/index.js` `digestCatalogEntries`: entries are JSON-quoted rather than joined by a separator because every separator is a legal description character; only quoting makes the boundary exact.
