# AGENTS.md — browser-use-chrome-devtools-mcp

## Rationale

- `package.json` `optionalDependencies.chrome-devtools-mcp` is pinned to the exact verified version (`1.9.0`, not `^1.9.0`): the launch arguments, tool catalog, and outbound-network closing flags this provider builds were read against that one build; a silent minor/patch bump could add a tool, rename a flag, or change a default before this provider is re-verified against it. It is `optionalDependencies`, not `dependencies`, so a deployment that never mounts this provider never installs a Chrome-automation surface, and pnpm skips it entirely on a platform where it has no matching optional variant. Installed with `--ignore-scripts` project-wide: the package's own `scripts` carry no `preinstall`/`install`/`postinstall` (only `prepare`, which registry installs never run), so nothing is lost by the blanket flag, and no third-party code executes at install time.
- `src/index.js` `resolveServerEntry`/`apply`: a missing optional server (module resolution fails and no `entryPath` was given) logs exactly one `ctx.logger.warn` naming the pinned version and the `entryPath` escape hatch, then `apply` returns without registering anything — no `browserUse` provider, no `mountSessionMcp` listeners, no tool-mask machinery. That keeps a deployment that has not installed the optional dependency (or is running where the platform excludes it) inert rather than failing tree boot. A bad explicit `entryPath` (given but not found on disk) and a malformed `Config` both still throw at plugin load: those are deployment authoring mistakes, not absence, and should fail loud rather than degrade.
- `--isolated` (never `--user-data-dir`, never `--executable-path` pointed at the user's real Chrome install unless a deployment explicitly configures it) matters because the model's browser must never share cookies, local storage, or login state with the person's own Chrome: a live two-session run (`.gm/scratch-sub70/cdt`) confirmed with real cookies that concurrent launch-mode Sessions get fully separate temporary profiles (`%TEMP%\puppeteer_dev_chrome_profile-*`), each cleaned up when its Session disposes, and that a page in one Session's browser cannot read a cookie set by another Session's browser.
- `excludePresets` exists because not every Agent should carry a browser: a `minimal` two-tool coding preset gains nothing from 29 extra tool schemas in every request, and per-agent MCP cost (see below) is not free. The set is checked once per `agent/created` against `ctx.get('agentPresets')?.composedPreset(agent.ctx)` (the same call `tool-agent-team` makes for its own exclusion), threaded through `mountSessionMcp`'s optional `excludeAgent(agent)` predicate in `@freddie/freddie-experimental-browser-use-runtime/mcp` — an excluded Agent never enters the MCP client, never reserves an attachment slot, and gets no tool-mask overhead either. Confirmed live: a `standard`-preset Agent got 29 `mcp__chrome-devtools-mcp__*` tools; a `minimal`-preset Agent in the same boot got zero, with the MCP node-process count unchanged (no server even started for it).
- Per-agent MCP cost: `mode: launch` starts one `chrome-devtools-mcp` Node child (and, lazily, one Chrome process tree) per live Agent that is not excluded — this includes every subagent and workflow child that joins its own Agent identity rather than inheriting a parent's composition. Measured live: agent creation itself resolves in tens of milliseconds; `agent.whenIdle()` (which now also waits out MCP discovery, see below) settled around 1–2.5s cold and included full Chrome+MCP-server startup. Chrome launches lazily at the first browser tool call, not at Agent creation, so an Agent that never calls a browser tool never pays the Chrome-launch cost, only the MCP-node-startup cost paid once discovery runs.
- Catalog-race fix: freddie's `agent/created` does not await listener promises and the agent loop snapshots the tool catalog before its first model request, so a naive "await discovery inside `system-prompt/assemble`" (the previous shape) was too late — the first request already read a catalog with no browser tools, and only the second request (after `system-prompt/assemble` had run once) saw them, defeating provider-prefix cache reuse for that Session's very first request. `mountSessionMcp` now holds a freshly created, not-yet-running Agent in a `runMaintenance` phase until MCP discovery settles (or the Agent's own lifecycle aborts), so the very first turn already carries the complete catalog. An Agent that is somehow already running at the moment it is announced (never observed in this harness's own creation path, but not structurally impossible for a future caller) cannot be held this way and may still see the catalog land on its second request.
- Server-side network closure: this package cannot silently vendor a "trust the server's own defaults" stance — a fresh `chrome-devtools-mcp` install and a fresh launched Chrome both make unprompted outbound requests on their own. The provider now passes `--no-usage-statistics --no-performance-crux --no-source-maps` (closing the server's own usage-stats/CrUX/source-map fetches), sets `CHROME_DEVTOOLS_MCP_NO_UPDATE_CHECKS=1` in the child's env (closing the server's own npm-registry update check, which otherwise spawns a detached `check-latest-version.js` process and writes `~/.cache/chrome-devtools-mcp/latest.json`), and in `launch` mode passes one `--chrome-arg=--host-resolver-rules=MAP <host> ~NOTFOUND, ...` covering every host a stock headless Chrome instance contacted unprompted in this harness's own live measurement (`update.googleapis.com`, `*.gvt1.com`, `android.clients.google.com`, `mtalk.google.com`, `clients2.google.com`, `csp.withgoogle.com`, plus `optimizationguide-pa.googleapis.com`/`clientservices.googleapis.com`/`safebrowsing.googleapis.com`/`content-autofill.googleapis.com`, which Chrome's own component-update/Safe-Browsing/autofill services reach on a longer-running instance even though this harness's short runs did not exercise them). `--disable-features=Translate,...` Chrome already carries by default (see the harness-observed `chrome.exe` argv) closes several more surfaces (translate ping, MediaRouter discovery) without a flag from this package. Attach mode connects to a browser the deployment already runs and does not own its launch flags, so these switches apply to `launch` mode only.
- Not closable by flag: Chrome's built-in `GoogleUpdater` (`updater.exe`) is a separate OS-level scheduled task on a machine where Google Chrome is the system install, independent of any one launched Chrome process and outside this package's process tree entirely; it is not spawned by or as a child of the MCP server and this package neither starts nor can stop it. `--isolated` avoids attaching this launched browser to that updater's managed profile, but the updater's own background wake-ups are a machine-level fact, not something `--chrome-arg` reaches.
- `mcp__chrome-devtools-mcp__*` tool calls are not gated by an approval prompt under the default `workspace-write` preset, and cannot be, by the shape of the existing approval mechanism: `packages/core/tools/src/index.js` `prepareExecution`'s `tools/pre-execute` waterfall defaults to `{ kind: 'allow' }` for every tool unless some listener returns `ask`/`deny` (no such listener is in the default `freddie-base` bundle composition — `auto-review` only activates for a session that has explicitly switched to the `auto` preset, and `hooks-claude-code`/`hooks-codex` are not mounted by default at all). The only approval trigger `workspace-write` carries by default is sandbox escalation (`packages/sandbox/sandbox/src/escalation.js` `approveEscalation`, invoked from inside `tool-bash`/`tool-pwsh`/`tool-fs`'s own `execute` bodies when the model supplies a widening `sandbox_permissions` argument) — that is the same "ask only on escalation, not on every call" behavior this provider's tools share with ordinary bash/pwsh/fs calls under `workspace-write`. The asymmetry: bash/pwsh/fs start at a narrower mode (`read-only`/`workspace-write`) and require an explicit approved escalation to reach `danger-full-access`, while `mcp__chrome-devtools-mcp__*` tool schemas carry no `sandbox_permissions`/`justification` fields at all (confirmed against the live-fetched schemas) and this provider offers no narrower starting mode to escalate from — a launched, isolated headless browser is a single fixed capability level with no existing lever in the escalation ladder to attach to. Extending the `WIDER_MODES` ladder to MCP-sourced tools would be a cross-cutting change to `packages/sandbox/sandbox` and `packages/mcp/mcp-client` (whose own docs describe the ladder as a bash/fs/terminal-specific "enforcement dialect", not a generic tool-registry concept), so this package reports the gap rather than attempting a narrow, package-local workaround.
