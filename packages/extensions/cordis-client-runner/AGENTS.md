# @freddie/freddie-cordis-client-runner

## Rationale

- `client/evaluator.js`: evaluating a definition's browser half is this package's product; the `new Function` wrapper mirrors the host precheck exactly (line offsets match) and the source arrived from a host process that accepted and prechecked it. A browser-only `SyntaxError` keeps just the engine message. `process` and `Buffer` are bound to `undefined` (`NODE_GLOBALS_HIDDEN_FROM_PACKAGES`) so `typeof process` probes stay safe.
- `client/guard.js`: shadowing slot kinds get a page-local rank (later registrations first); chain slots keep their own election. `env.claim` runs only after the registry accepted a registration (a rejected one seats no entry, so no crash could name it). `theme.overrideTokens` keeps the documented two-argument shape but the source value is replaced, never trusted.
- `client/index.js` is the one place the Client and Host planes meet: it mounts the `dynamicCordisRunner` namespace and re-exports its payload vocabulary so this package names what it sends without importing a Host package.
- `sync` no-ops without a `connection`: tree teardown disposes it and the provider cleanups publish a final manifest the API layer would reject; a live reconnect still republishes.
- `invoke`: the namespace codec rejects non-JSON model arguments with a bare field name; only this layer knows the call, so it adds the teaching. A carrier error means the call never reached the host half; `ok: false` is the host half refusing. The seam names business payloads only, so carrier failures fold into each verb's own failure shape; `resolveRequestRun` throws because `answer` logs and drops failed answers while the host settles on its own.
- `reportRenderFailure` is fire-and-forget: the run was answered before render, and a failed report must not turn one crash into two.
- `client/runtime.js`: the supervision seam fires for every entry crash on the page (factory UI included), so only components this runner seated are reported. The host keeps the last crash across pages for the model; `failures` is what this page shows now; neither derives from the other.
- The per-package operation queue tail swallows failures so one rejection cannot wedge later operations on that package. Loading invalidates the module then registers (the module table throws on duplicates). The live record is seated only after settle so an error mirrored during `apply` cannot claim the package is live; settled-but-inactive means pending on an unsatisfied declaration.
- `client/timer.js` `ClientTimerService` keeps the vendored Host `TimerService`'s erased callback tuples and arbitrary async-iterator return/rejection types; narrowing them would change the public API.
- `client/slot-catalog.js` `CLIENT_SLOT_API` repeats register options and framework props verbatim per seat: that sameness is the contract a registrant reads, so `jscpd:ignore` skips the data.
- `client/runtime.js` `bounded`/`cancellers`: evaluation and activation of a browser half have a deadline and a canceller because a closure or `apply` that never settles otherwise holds the per-package queue forever; `retract` cancels the pending load first so a stop never waits behind the code it is stopping.
- `client/runtime.js` `abandon`: a failed or timed-out load removes its loader entry without awaiting it, because disposing a fiber whose `apply` never settles never resolves.
- `client/runtime.js` `mount`: the page-local render failure is cleared when a load starts, not when it ends, since a component that crashes while the entry is being seated reports before the load settles.
- `client/runtime.js` `onEntryError`: repeated crashes of one package are one row with a count, and only a changed slot or message is reported to the host again; the host keeps the latest per package anyway.
- `client/guard.js` `heldCell`: in keyed and list seats a registration whose `key`/`id` is already held by any other registrant (a built-in entry or another dynamic package) is rejected before the registry sees it. The registry itself only refuses an equal priority, and the guard hands every dynamic registration a lower priority than anything seated, so without this check a dynamic package that reused `cordis-panel` shadowed the real panel out of the sidebar. Ownership is component identity in `owners` (`claim` runs after acceptance), so a package's own earlier entries never count and it can re-seat its cell; a built-in holder has no owner. Single seats have no cell name and stay replaceable on purpose (their catalog `replaceRisk` says so).
- `client/runtime.js` `reported`: the guard reports each distinct rejection message once per mounted package, because a `slots.inject` callback re-runs on every redeclaration of its seat and would otherwise repeat the same report indefinitely.
- `client/guard.js` `STRUCTURAL_SLOTS`: `root` and `sidebar` are single slots holding the navigation, Settings and the plugin panel; a package that registers there (even an empty component) removes the only controls that can stop it, so the guard rejects it and teaches the alternative seats.
- Not a security boundary: guard/facade is API discipline; a dynamic package is as trusted as the host process that accepted its definition. Nothing loads on activation: a dispatch (model `cordis_run` or a card start control) is the only load trigger, so a page refresh starts clean while host memory keeps the definition.
- `client/runtime.js` loads converge by Plugin Run ID against live state: the exact live activation is a no-op that still answers, another run replaces it, the same Package after a retract loads afresh; per-package serialization prevents interleaving. Unload = loader entry removal (fiber disposal cascades slot entries and facade effects) + module invalidation + style removal. `wrap` keeps the plugin's OWN object-form `inject` as the facade's service gate (function form declares none, so reaches no service).
- `client/runtime.js` `owners` (component identity -> package): attribution cannot use `entry.registrant` (package-suppliable, would allow impersonation) or the shadowing priority (absent on chain entries), and must survive teardown between crash and report. Components never collide across packages (separate closures); a same-package double seat maps to one identical id.
- `client/guard.js`: `SlotRegistry.register` must stay a prototype method and run with the traced receiver so effects land on the CALLING plugin's fiber. `theme.overrideTokens` also hangs the layer disposer on the calling fiber (contract: unload restores; model code cannot be trusted to keep the handle).
- `client/evaluator.js`: the package source is the body of an async function whose parameters are the symbol surface; shadowed globals (`setTimeout`, `fetch`, `require`, `React`, ...) throw teaching redirects, and `DYNAMIC_CLIENT_REDIRECTS` is shared with the render-crash message so `window.setInterval`-style bypasses get the same redirect. `React` redirects to the `tool.view.cordis` webjsx contract (plain function returning JSX, or an HTMLElement subclass via ui-primitives `defineElement`). `host.call(method)` with no argument delivers `null` (wire is JSON; `{}` would invent an argument). Host prechecked syntax at define time; client SyntaxError handling is the engine-divergence fallback.
- `client/index.js` wire-refusal teaching: the codec names the refused field but not the call, so the runner adds the call and the contract.
- `client/api-catalog.js` and `client/slot-catalog.js` are hand-maintained data; `scripts/gen-cordis-api.ts` / `gen-client-catalog.ts` no longer exist. The slot catalog carries strings only (the one meeting point of the two planes; never client imports).
