## Rationale

- `src/run.js` stdin close: a concurrently closed stdin does not change range ownership, so its failure is swallowed before `child.terminate()`.
- `src/run.js` stderr forwarding: synchronous `writeFileSync(process.stderr.fd, ...)` preserves byte order without owning a backpressure queue (a slow host sink can block the event-loop turn). Host stderr is an observation sink, never a child-run failure authority; a stderr stream error is ignored because JSON-RPC and `child.done` remain the only terminal authorities.
- `src/run.js` one-turn `setImmediate` yields: stderr already queued by an exiting process must reach the Host before forwarding listeners detach or the result settles; Node reports stdout EOF before the child close that owns the outcome, so an exiting process gets one I/O turn to publish its facts before rollback; frames already queued by the exiting app-server stay authoritative before process exit ends the run.
- `src/run.js` `processFailure.catch(() => {})`: a normal post-result dispose also closes the process, so its expected late rejection is kept observed when the terminal result settles first. When exit observation fails after a wire failure, the wire failure stays authoritative.
- `src/wire.js` `fatal`: fatal protocol state can arrive after the current guarded operation settled, so the shared rejection is kept observed without adding another promise-adoption hop to active races. Both pipe `error` listeners live for the per-run streams' lifetime so a late `EPIPE` or read failure never becomes an unhandled `EventEmitter` error.
