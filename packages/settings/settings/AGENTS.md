## Rationale

- `src/index.js` `applyPathOp`: the empty path addresses the section itself. Unsetting through an absent path is already satisfied; setting through one creates the intermediate objects. `clone` un-marks `visiting` on exit so one object referenced twice without a cycle passes.
- `src/index.js` write path (`mutate`/`merge`/`replace`): a mutate's ops array is wrapped so one JSON-shape walk covers every mode. The payload is snapshotted at call time (the queue must never read a caller-owned object the caller keeps mutating) and the same walk rejects values JSON cannot preserve (`cloneJsonShaped`).
- `src/index.js` write queue: each write chains past a failed predecessor (`previous.catch`) so one rejected write cannot poison the namespace queue. Every mode derives from the section as it stands at the front of the queue, and the `expectedRevision` check also runs there: the queue orders writes but cannot tell a fresh writer from one holding a snapshot a predecessor already superseded.
- `src/index.js` after `persist`: the cache is updated whether or not the registration survived (the write reached storage); the revision bump and notification happen only if this registration still owns the namespace and the service is not stopped.
- `src/index.js` `publish`: every raw section is read before the document swap so the revision bump compares stored-before with now-after; an external edit moves the revision exactly like an in-process write. A malformed stored section counts as absent for "before" (and as "no user layer" in the read at the `catch` near `user = undefined`, which already warned at publish and kept the last good value) so those reads stay total.
- `src/index.js` `resolve`: the merged candidate is untyped; the `schema(...)` call is the runtime validation, and the owner's `validate` runs on the admitted value so it sees defaults and the composition base exactly as the owner will.
- `src/index.js` change notification: invocations of one watcher callback are serialized per watcher in commit order so a slow stale invocation cannot apply after a newer one; the activity check runs when the queued invocation would start, so a disposer or service stop that ran meanwhile prevents the start, and started invocations drain at service dispose. Listeners are fanned out one at a time (plain `emit` stops at the first throw); invariant violations are harness-fatal and rethrown after every listener ran, any other failure is contained so one observer cannot wedge the commit path or a provider's reload loop. An async listener's rejection cannot reach the synchronous rethrow, so it is contained separately.
- `src/index.js` service teardown: refuse new writes and watcher starts, then await every queued write chain and started watcher invocation so disposal completes only when storage and observers are quiescent; queued-but-unstarted invocations skip through the stopped check.
- `src/index.js` consumer binding (`isUnloading`): the disposer runs both when a settings provider detaches (consumer keeps running and must fall back to its composition entry) and when the consumer itself unloads, where `onChange` would re-register routes and touch resources being released. The watcher callback has the same hazard for a stored change landing mid-unload, hence the guard in both places.
