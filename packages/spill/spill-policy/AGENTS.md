## Rationale

- `src/index.js` load: `maxInlineBytes` is validated at load, not per call, because a negative or fractional cap would reach `TextRetainer`'s `assertBudget` and turn every oversized-result call into an `isError`; a bad config must fail the deployment, not the tool. Omitted means no automatic spill policy (nothing registered).
- `src/index.js` spill failure: saving is best-effort; a storage failure (permissions, ENOSPC, backend down) must never fail the call or hide the content, so the original stays inline.
- `src/index.js` notice reservation: the notice's byte cost is reserved inside `maxInlineBytes` so preview + blank line + notice never exceeds the documented cap. The reserve is priced at the worst-case omission count (the full byte total); its digit count bounds the real one, so the final notice is never longer than reserved. `\n\n` is the 2-byte join.
- `src/index.js` cap invariant: the policy never emits a replacement larger than the cap. If the notice alone exceeds it (tiny cap or long spill root) the inline content is kept; a within-cap replacement is always smaller than the original (which exceeds the cap by entry condition), so one check covers both. The already-written spill file is a harmless orphan; cleanup is deferred.
- `src/index.js` `tools/post-execute`: delegates to `next()` first so a downstream listener (for example a hook) settles the result; only accepted plain-text results are shaped and a block passes through untouched. `read` is skipped to avoid a read, spill, read-again loop.
- `src/index.js` `tools/code-dispatch-log`: bounds only the session log's copy of an oversized sub-call result; the program's returned value is untouched (it already crossed the worker boundary whole), and replay/UIs read the full text through the spill artifact as for native spills. `read` sub-calls do spill here: the log copy is not model context, so the loop above cannot happen, and `read` is what produces huge logs.
