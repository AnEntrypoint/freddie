## Rationale

- `src/client/index.js` `apply`: the journal is the `globalThis.__FREDDIE_HMR__.events` array itself, reused rather than copied, because a self-reload or in-document shell remount builds a new driver in the same window, and the rows leading up to it are what a developer reads afterwards.
- `src/client/index.js` `wireGraph`/`remountShell`: the host's graph (sent on each SSE connect) is patched per rebuilt row and written back to `__FREDDIE_BOOT__` before a remount, so the new AppWebEntry never boots a stale rev.
- `src/client/index.js` `queue`/`enqueue`: reloads are serialized because frames can arrive faster than a swap completes and interleaved dispose/execute chains would corrupt the single-slot handoff.
- `src/client/index.js` `handle`: unknown frame types are ignored on purpose (the frame union is merge-extensible; newer hosts may send types this bundle predates).
- `src/index.js` `watchRow`: the module host hashed the tree before publishing the graph, so `rehash` runs right after the baseline snapshot; otherwise a write in between becomes an already-current baseline paired with a stale graph rev.
- `src/index.js` bundle watch: `syncWatches` has no self-exemption; this plugin's own row is watched like any other, so a modules/hmr rebuild rides the same chain. Initial sync covers rows already in the graph, the `onGraphChanged` subscription covers later ones.
- `src/index.js` `EVENTS_ENDPOINT` handler: named routes match ahead of the fallback carrier's GET/HEAD gate (`frontend-static`), so the handler repeats it (HEAD 200, other non-GET 405).
- `src/index.js` `cssListener`: without a `cssManifest` service there is no `/styles/app.css` link to swap, so a stylesheet change is published as a `shell-rebuilt` frame (root `styles`) instead of `css-rebuilt`.
- `src/invariant.js` `install`: the `internal/plugin` listener is async on purpose; `emitPluginDisposed` (framework/cordis fiber.js) logs rejected promises returned by listeners, so a violation surfaces loudly. The `oxlint-disable` line silences the resulting misused-promises rule.
- `src/client/index.js` `verifyTree`/`reportTreeFailure`: a rebuild that leaves no throwing fiber can still leave the tree inconsistent (a mount fiber FAILED, an entry pending, an empty root), so after every rebuilt or remount frame the shell's `health()` decides; an unhealthy tree first gets one in-document remount, and only a tree that still fails is reported through the boot page and given one automatic reload.
- `src/client/index.js` `AUTO_RELOAD_KEY`: the automatic reload is spent in `sessionStorage` before it happens and refunded only when `health()` next passes, so a failure that survives a reload stops at the visible report; unreadable storage counts as spent because an unguarded reload could loop.
- `src/client/index.js` `verifyTree` logs with `console.error` instead of `ctx.logger`: a remount replaces the Context that owns the exporter, so the stale closure's logger writes into a buffer nobody reads.
- `src/client/index.js` `apply` debug state: `window.__FREDDIE_HMR__` holds one `events` array that every driver appends to in place and one `status` object each new driver installs as its own live reference. A self-reload or shell remount leaves the previous driver's async chain (`reload`, `verifyTree`) running in its old closure, and it keeps recording afterwards; a per-driver journal republished as a snapshot let that stale chain overwrite the new driver's `event-source-open` row and its connected status until the next heartbeat. The shared array keeps every row in real order, and a tree verdict reached by a stale driver is written to `liveStatus()`, the current driver's status, because its own status object is already detached.
- `src/handles.js` and `src/invariant.js`: the disposal audit counts only what the `client-hmr` fiber itself opened. `openWatcher` records each `fs.watch` watcher and removes it on the watcher's own `close` event; `startInterval`/`stopInterval` record and clear each interval. The ledger hangs off the fiber under `Symbol.for('freddie.client-hmr.handles')`, so a host hot replacement that re-imported the plugin module still shares one ledger with the companion. A process-wide handle census would move whenever any other plugin opens a watcher or timer, and the old `StatWatcher` census could never fail because nothing here calls `fs.watchFile`. The audit waits one `setImmediate` after `fiber.await()` because `FSWatcher.close()` emits `close` on the next tick; interval bookkeeping is by disposer, so an interval cleared without `stopInterval` is not seen.
