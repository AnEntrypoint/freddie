# @freddie/freddie-client-modules

Client module system: the browser peer of Node's internal ESM loader. The web shell mounts the framework cordis Loader for entry governance (fiber lifecycle, inject waiting, update/refresh) and injects this package's `ClientModuleSystem` through its `internal` contract — the Loader side's only consumption point is `EntryTree.import`, so replacing `internal` replaces exactly "how plugin code arrives" and nothing else.

Native ESM model: a plugin is real `export`s loaded through a real `import()` against its served URL, `/plugins/<id>/~<rev>/<entry path>`. The page's one import map, generated from the same boot graph, resolves every bare specifier a plugin imports: each graph row's package name and its `<pkg>/client` alias, each row's `freddie.client.external` request that is not itself a row (a workspace wire module such as `@freddie/freddie-session/surface`, served at `/workspace/<specifier>`), and the third-party npm specifiers `vendor-modules` contributes. Module body side effects, CSS injection included, run at `import()` time under the browser's own sequencing; there is no registration step and no synchronous `require`. `<id>/client` and the bare id resolve to the same exports, because a plugin's entry IS its package's client half.

The shell kernel builds the module system before Cordis exists, since the mechanism that loads plugins cannot arrive through itself: `AppWebEntry` (`web/src/boot.js`) imports this package directly and calls `createClientModuleSystem({ boot, staticModules })` with `window.__FREDDIE_BOOT__` and the platform seed, so a missing or malformed graph fails the boot. This package's Cordis `apply()` only enrolls that existing instance as `ctx.modules` and throws when it did not run first.

Resolution branch order (`import(specifier)`): platform seed word → the shell's instance; memoized record → its exports; graph row → `import()` its served URL (concurrent callers share one in-flight import); anything else throws, the runtime mirror of the import map. `prefetch(id)` is the stage-one arrival hook: it imports a row without returning it. A changed row is served from a new URL (its `/~<rev>/` segment changes), so `import()` fetches fresh bytes; `invalidate` drops only this system's record, and `updateGraphRow` swaps a row before the hot-reload prefetch. `register(id, exports)` seats a module that has no URL, such as the dynamically evaluated packages of `cordis-client-runner`, and rejects a duplicate id.

The Node half scans enabled Loader entries for web `freddie.client` packages, resolves each `exports["./client"]` (which must live under the package's `src/`), hashes the package's whole `src/` tree into the row's rev, carries package-specific `freddie.client.external` requests, orders requested package rows before their consumers, and serves every file of that tree under `/plugins/<id>/~<rev>/<path>` (HEAD returns the GET headers and no entity body). The row's URL is the entry's real path under that prefix, so every sibling import a plugin makes resolves under the same rev segment: a request naming the row's current rev answers `cache-control: public, max-age=31536000, immutable`, any other or absent rev segment answers `no-cache`, and every response carries a strong size+mtime `ETag` honoured as a `304`. There is no `client.js` alias and no redirect. The boot injections carry one `modulepreload` hint per script under the entry directory of each `immediately` row (measured to win at an emulated 40ms RTT; hinting every row measurably loses), and the import map points a workspace wire-layer specifier at its real served path rather than at the `/workspace` route's redirect. Client entry directories missing on disk are reported together in one package/path list, and unrelated failures are listed separately.

`freddie.client.external` is an optional exact-specifier request list beyond the implicit baseline: the shell-seeded platform modules (`webjsx`, `@freddie/cordis`, `ui-slots`, `ui-primitives`) plus the parser-preloaded `runtime/client`. A request is answered by the graph row it names or, failing that, by a workspace wire module served at `/workspace/<specifier>`; only a trailing `/client` aliases a package row, and there is no provider-alias declaration. `import type` requests nothing. Composition rejects malformed requests, self-requests, and cycles; ordering places every requested package row before its consumers. See [shared modules and the module graph](../AGENTS.md#shared-modules-and-the-module-graph).

## Model Experience

None, as the module loader is browser-side kernel machinery; nothing here reaches a model request.

#### KV Cache effect

None; this package neither assembles nor sends a provider request.

## Known Limitations and Deferred Work

- **Flat module graph by design** — every row is one module node loaded from one URL, and the browser's own module cache does the memoization, so the externalization granularity can change through import-map entries and graph rows without an interface change.
- **No unload bookkeeping of its own** — style removal and fiber teardown ordering live with the HMR driver (`@freddie/freddie-client-hmr`); the module system only inventories the owned style tag ids per record.
