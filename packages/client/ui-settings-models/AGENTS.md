# client-ui-settings-models

## Rationale

- `src/client/index.js`: the settingsScope injection makes ui-settings activate first and remote dispatch preserves listener order, so its `settings/document-updated` listener starts the mirror refresh before this store joins that refresh.
- `src/client/OnboardingModal.js`: Modal's one-shot factory appends a NEW `freddie-modal` to `document.body` per call and nothing removes the previous one; the step re-renders on every store change, so the modal is cached in a module-level singleton (`cachedModalEl`, size-1 like `DetailsPanel.js`'s `cachedArgsBlock`) and re-rendered in place. Onboarding shows at most one modal at a time.
- `src/client/OnboardingModal.js`: the application root is set inert while the step renders, and the component returns `null`; returning the body-portaled element would let the parent renderer move it under `#root`, making the dialog's own controls inert too.
- `src/client/ProviderEditor.js` credential retry: a settings success advances both retry baselines immediately. Keeping the derived fields in the draft prevents a pushed namespace refresh from turning them into deletions when the following credential write is retried.
- `src/client/ProviderEditor.js` string fields: whitespace-only input is cleared, not stored; `stringAt` already reports it absent, so otherwise the field renders empty while the draft carries the spaces into `settings.yaml`, where both adapters would accept them as a real value.
- `src/client/ProviderEditor.js` API key input: submit validity is updated on `input` because `change` fires only after blur, which loses the first click on Save.
- `src/client/DeepSeekModelsEditor.js`: capacity parsing snaps near-integers (`2.3 * 1e6` lands a few ULPs high in binary floating point); row error keys embed the row index, so `remove` re-keys around the dropped row and reset clears them all.
- `src/client/ModelsSection.js`: the post-apply notice is keyed by route id (the one thing an apply cannot change) and announced only after the refreshed directory is in the snapshot, because an apply can rename the route and the target captured at card open carries the old name; a row the same apply removed keeps the captured identity.
- `src/client/ModelsSection.js`: only the adapter can tell a hand-declared route from a shipped one it also has a stored profile for, so the custom tag follows its answer and stays off when it gives none.

## Design notes

- `apiKey.js` mirrors `normalizeApiKey` in `@freddie/freddie-llm` (printable ASCII, no space); client packages import only client packages, so keep the two in step, likewise `validateDeepSeekModels` with the host's `catalogModel`. The pasted `NAME=value` env-line heuristic (upper-case name, `=` not followed by `=`, so `sk-` keys and base64 `ABCD==` pass) runs only here: a resolver applying it could lock out a gateway whose key legitimately has that shape. Empty key field is valid (keep the stored key); whitespace-only is a failure.
- `DeepSeekModelsEditor.js`: settings replace `models` as one array, so the parent supplies effective inherited rows until the first edit materializes a user override; reset removes the override instead of copying defaults. Capacity input accepts `256K`/`1M` (1M = 1000K), stored as a plain token count; blank = inherit (`undefined`), unreadable = `NaN`, rejected by `validateDeepSeekModels`.
- `EditorFooter.js` renders only what it is handed; cards own commit gating and in-flight wording. Cancel refuses input only while a commit is in flight, never when the card is disabled.
- `index.js`: refetches the snapshot only after first load (an unopened page must not fetch on background invalidations); ui-settings' apply declares `settings.section` with unconstrained activation order, so registration goes through `slots.inject()`.
- `ModelsSection.js`: a whole-section provider without a key renders its setup card only in the first-run posture (no usable provider) and until closed; each card kind owns its open state so closing one never discards another's draft; setup-card dismissal falls back to a row (reopen via Edit). Provider removal unsets the credential first, then the settings profile (both idempotent, so a second-step failure is retryable), naming the profile rather than rebuilding the namespace.
- `OnboardingModal.js`: no unmount signal exists; the step's null branch must call the release function (idempotent). The onboarding host renders at most one step (`find`, not `filter`).
- `ProviderEditor.js`: a typed key stores via `credentials.set` under the profile reference, deriving `<ROUTE>_API_KEY` when none. Reasoning effort is deliberately absent (per-model capability; the composer picker offers each model's levels; `settings.yaml` keeps the profile field). Edits are minimal `settings.mutate` path ops against the stored section, because the draft comes from the redacted descriptor and a wholesale replace could delete fields the card cannot see. Catalog reset baseline is the layer beneath the user override (composition pin or schema default), not the effective value, which still echoes the override until the unset applies.
- `store.js`: `llm.providers`, the settings mirror and `credentials.describe` join into one snapshot; latest load wins; a failed settings refresh reuses the mirror's held view. A row is usable when its route is registered and any credential its profile names is stored; profiles naming no reference (Bedrock chain, Vertex ADC, keyless gateway) owe no key. Onboarding readiness: any usable provider ends it; otherwise the official DeepSeek route decides whether prompting for a key can help.
- `welcome-store.js`: the welcome scope is the transport (loopback follows the durable Host section; a remote memory-mode scope never answers and the acknowledgement stays process-local). A malformed durable value reads as an empty section (unacknowledged). `onboarding-copy.js`: bump the version only when the notice changes materially; comparison is exact equality. `WelcomeNotice.js` is created fresh per snapshot, so its "finished" guard lives on the store (`state.acknowledged`).
- Custom elements here replace former React components: state is instance fields, re-render is `applyDiff(this, vdom)`. `invariant.js`: nav-entry-only section plugin, no events, no cross-plugin mutable relation.

## CSS rationale

- `ModelsSection.css`: every color resolves through a `--freddie-alias-*` token; bare `--border` / `--surface` / `--text-*` names (and `--freddie-alias-border-subtle`, `-text-tertiary`, `-text-primary`) are undefined in this app and would render their light-mode fallback literals under the dark theme. The app has no global border-box reset, so controls set `box-sizing` themselves or the outlined variants stand 2px taller than the filled ones beside them. The catalog is a table whose caption strip is hidden from assistive tech because each field already carries an indexed `aria-label`; data-URI SVGs cannot resolve CSS variables, so the select chevron uses the caption gray `#81858C` shared by both themes; the native disclosure marker is replaced by a rotating chevron because the engine triangle differs and cannot take the label color.
