# AGENTS.md — ui-theme

## Rationale

- `src/client/AppearanceRow.js` `FreddieAppearanceRow.setProps`: `props.useStore` is a framework hook bound per instance by the slot renderer and cannot run outside a render, so `setProps` calls it once, synchronously, to capture the selected preference for `#render()`. `FreddieEntryHost` (ui-renderer `scoped-slots.js`) re-invokes `setProps` whenever its `entryProps` object is reassigned. Selection follows the persisted preference, never the resolved active theme.
- `src/client/index.js` `injected` (settings row): the store is re-synced from `theme.getTheme()` at injection so no `theme/change` event is lost between registration and first render; the store's revision guard drops stale duplicates.
- `src/client/index.js` `ThemeService`: `light`/`dark` are built in (base stylesheets carry both palettes); third-party themes register alias-layer overrides; duplicate ids throw and `system` is a preference, not a registrable id. Preference writes go only through `setTheme`; continuous sync only through the `theme/change` event. Disposing the theme backing the active preference resets to the default. The service never touches the DOM (ui-layout's presenter consumes the snapshot) but holds the `prefers-color-scheme` query and re-emits when the OS flips while the preference is `system`.
- `src/client/index.js` `overrideTokens`: token-level analogue of slot shading. Layers stack in `seq` order, later layers win per token, removing a layer restores what it covered; re-calling with the same source replaces that source's layer and restacks it on top; the disposer is a no-op once the source re-overrode. Input is validated at runtime (model-authored callers pass untyped JS through the dynamic-package facade); a bare string value throws a teaching error and the stored layer is a defensive copy. With no layers the registered definition passes through by identity.
- `src/client/index.js` `remote` inject: carries the forwarded settings invalidation that `ctx.settingsScope.bind(spec)` subscribes to on this context.
- `src/boot-theme.js`: the bootstrap is an inline script right after the opening body tag (before the shell mount and module script); each index render embeds the durable built-in preference and the browser resolves only `system`, writing the same DOM fields ui-layout's ThemePresenter owns after the client plugin tree activates.
- `src/client/AppearanceRow.js` cube order: Light, Dark, System (figma 501:30015-30017).
- `src/invariant.js`: no runtime invariant. The settings scope validates and publishes the durable theme section and the registry emits `theme/change` synchronously with its mutations.

## CSS rationale

- Scrollbar contract (`styles/scrollbar.css`): rules sit on `body`, not `html`, because `design-platform.css` declares the `--freddie-alias-*` tokens on `body` (dark overrides on `body[data-ds-dark-theme]`) and custom properties inherit only downward, so an `html` rule would resolve them to the guaranteed-invalid value. Surfaces choose their elevation by rebinding `--freddie-scrollbar-thumb` / `-thumb-hover` from the base l1 pair to the l2 pair on the elevated container, so it inherits down to whichever descendant scrolls; consumers are Menu, ModelSelect, PopupSelectView, MenuView, TodoPanel, ApprovalPanel, InputBar, QuestionComposer, PlanReviewPanel, AttachmentRail, DirectoryBrowser, SettingsRoot, ModelsSection and SidebarRoot (`quietBars` rebinds to `transparent`).
- `styles/scrollbar.css` render paths: the standard (`scrollbar-width` / `scrollbar-color`) and `::-webkit-scrollbar` paths are mutually exclusive, and the gate is load-bearing. A non-`auto` `scrollbar-width` or `scrollbar-color` makes Chromium and Safari drop every `::-webkit-scrollbar*` rule for that element, including the `:hover` thumb (measured: an 8px webkit width took effect alone and was ignored once `scrollbar-width: thin` was added), and Firefox has no hover pseudo-element. `@supports not selector(::-webkit-scrollbar)` therefore sends only Firefox down the standard path; an engine too old for `selector()` evaluates false and takes the pseudo-element path (correct for pre-16.4 Safari). The standard-path declarations repeat on every element (`body, body *`) because inheriting would pass down the color already substituted at `body`, so a descendant rebind could not change it (`scrollbar-width` is not inherited anyway); that path has no hover counterpart because the engine derives its own. The WebKit pseudo-element rules are not gated in turn (an engine without them drops them as unknown selectors) and are unscoped because they are not inherited; the track stays transparent so the thumb reads against any surface, and the corner matches it. `--freddie-scrollbar-width` mirrors the WebKit bar's layout width for surfaces that must align beside it (the overlay composer seat).
- `styles/base.css`: supplies variables the token sheets and component CSS reference but upstream (deepsuite `theme/global.css`) defines, so the composite `--dsw-font-*` variables resolve and motion rides the upstream curve; the code font stack (`--ds-font-family-code`) deliberately omits a bare `monospace` tail, because on Windows the generic family resolves to a legacy fixed-width font whose glyph metrics differ from the named code fonts. `styles/design-platform.css`: Figma's font-weight 510 (an SF Pro variable weight) always renders as 500 here, since non-variable webfonts snap intermediate weights unpredictably. `styles/shiki.css`: the token palette behind shiki's css-variables theme (`--shiki-*`, emitted by the ui-primitives `CodeBlock`); light on `:root`, dark on the body attribute like every token sheet, with background/foreground aliasing the markdown code-block tokens so highlighted and plain blocks agree.
- `styles/gradient-shadow-text.css`: exported by the `@deepseek-figma-plugin/custom-variable-name` plugin (shadows, blur filter, fonts); the `--dsw-font-markdown-code-block-small*` variables (12/18 code font inside the expanded tool row card) are hand-added, not plugin-exported, and a re-export must keep them.
