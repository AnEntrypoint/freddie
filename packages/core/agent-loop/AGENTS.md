# freddie-agent-loop

## Rationale

- `ReactLoopAgent.send` / `wakeDriver`: a waking message arriving while the current activity is aborted is routed to `next-turn` and its wake latched (`phase.wakeRequested`) for replay at convergence. The abort classification is captured before the inbox splice so a reentrant cancel from a splice observer cannot reclassify it. Maintenance phases latch the same way; a `disposed` abort reason never latches, so teardown waits on no model turn.
- `ReactLoopAgent.turn`: a first boundary whose waking message was removed, or whose `agent/pre-step` decision was rewritten to empty, still owns the initial turn boundary and ends `completed` without a model call. `max-tokens` is sticky: once a step hits the ceiling, a later normally-completed step must not downgrade the turn outcome. A follow-on turn gets a fresh `AbortController`, so a latch set on the old one is stale; the live driver claims the queue itself.
- `ReactLoopAgent.kick` (`containAtDriverBoundary`): reported failures and cancellation are already emitted (`agent/error`, `turn/end`); the driver swallows them so the `driver.resolve` chain never rejects.
- `ReactLoopAgent.buildRequest`: a fresh loop restores a persisted `reasoningEffort` only when the persisted provider/model equal the declared route and the value was not an adapter default; later steps re-resolve marked defaults through `requestProposal`. A `NO_ADAPTER` `LlmError` from `llm.prepareCall` is tolerated because middleware may serve an unregistered route; the terminal dispatch still requires an adapter.
- `AgentLoop` config `maxParallelToolCalls`: a getter reading the settings-section entry on every access. `runGroup` in `tool-calls.js` destructures it once per group, so a committed change caps the next group without disturbing the running one. `validate` runs `resolveMaxParallelToolCalls` (the schema admits any integer above zero) so a rejected value leaves the last good cap; `onChange` is a no-op because nothing is derived from the cap.
- `AgentLoop` constructor `hmr/before-reload` listener + `FactoryOwnership.markBusy`: hot reload deletes this plugin, disposing the fiber and aborting in-flight tool calls, which would end the turn with `ABORTED_BEFORE_DISPATCH` results and stop the agent mid-task. The listener vetoes while any agent is running; `onIdle` emits `hmr/idle` on the busy-to-idle edge only, which is what makes `framework/hmr` retry the deferred pass.
- `AgentLoop.restoreOrCreateConfigured`: a load is the per-id serialization barrier for eager write-behind and lifecycle retirement. Only a genuinely absent artifact (id not in `persistence.list()`) falls back to first creation; corruption and backend failures stay loud. `waitForDrainingConfiguredIdentity` waits only while the id still occupies `agents` or `sessions`; a live healthy occupant is a collision `create` / `resume` surfaces themselves.
- `AgentLoop.prepare`: callers reach it synchronously from a service method whose Cordis dispatch already requires the live factory fiber, or re-check ownership after their awaits (`resumeWith` does, after the persistence load); the `!isActive()` throw is only a backstop (the `v8 ignore` pragma there refers to this).
- `AgentLoop.prepare` `abort`: fuses caller cancellation, owner-fiber unload and factory teardown. It is registered before any resource exists, over mutable slots (`machine`, `detachSession`, `detachAgent`), so an unload arriving while the scope is still minting finds a working disposer instead of a leak. Every fused source carries an `Error` reason (`onCallerAbort` and `raceAbort` wrap non-Error caller reasons), which is why `assertLive` has an unreachable `String()` arm (pragma there).
- `AgentLoop.prepare` `dispose`: disposal is a `{ kind: 'disposed' }` cancel followed by `whenIdle()` quiescence. Work sent afterwards is the sender's bug: the registries are about to drop the agent. The owner-effect teardown returns early when `disposing` is already set, because the running disposal owns the same quiescence boundary and must not unregister the owner effect from inside itself.
- `AgentLoop.prepare` `publish`: a synchronous `announce` / `agent/session-start` listener may already have started teardown, so `assertLive()` rechecks liveness after each step; the machine itself is live from construction (delivery works from the `agent/session-start` extension point).
- `AgentLoop.resumeWith`: the persistence load may outlive its owner, so it races caller cancellation, owner-fiber unload and factory teardown (`raceAbortCall`); a never-settling backend cannot pin the identity, and a late-arriving preparation is disposed via `releaseAbandoned`.
- `tool-calls.js` `executeToolCalls`: each planned call owns a distinct `exec` object because `tools/execute` wrappers may replace `exec.signal`. Pre-execute and commit run in model order and may await; only dispatch overlaps. `appendToolResult` persists `result.meta` (the tool's private presentation payload, e.g. a result-time diff) so a UI bridge reproduces the card on replay.
- `invariant.js`: the `llm/stream` check listens with `RUN_BEFORE_SHORT_CIRCUITING_LISTENERS` (`prepend`) so a short-circuiting replay listener cannot silence it.
- `runtime-context.js` `project`: the cleared marker carries no `form` / `sections` on its `source` because it has no contributions left to attribute.
