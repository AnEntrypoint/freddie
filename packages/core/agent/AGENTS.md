# freddie-agent

## Rationale

- `Agents` constructor `ctx.accessor('agent', ...)`: the default `undefined` keeps `ctx.agent` readable on plain plugin contexts instead of hitting the Cordis unknown-property throw. Each `Agent.ctx` shadows it with an own property (own properties resolve before the context proxy), so the accessor never resolves a scope itself. It is effect-scoped and unwinds with the service fiber.
- `Agents.create`: a Service-backed factory is re-traced through the accessing context (`getTraceable`) so `AgentLoop` keeps its dependency origin while its effects bind to `ownerCtx`; plain factories receive `ownerCtx` as an explicit capability.
- `Agents.enter`: the `store.has(id)` check is the authoritative collision boundary; concurrent create/resume may both prepare, but only one exact entry can publish.
- `Agents.detachEntered` / `announce`: `announced` is set before the `agent/created` emit, so an entry rolled back before announce (never externally created) emits no `agent/disposed`, while a later `created` listener throwing after earlier ones observed it still gets its paired disposal. `announcing` is set before dispatch so a listener cannot recursively create a second lifecycle edge; a `detach` requested mid-dispatch is deferred until dispatch unwinds (`detachRequested`).
- `Agents.announce` vs `emitDisposed`: a synchronous `agent/created` listener failure is not caught, vetoing publication and rolling back; only returned-promise rejections are observed (logged), since they happen after that boundary. `agent/disposed` listeners are fully contained.
- `Agents.runWithInitiator`: `Promise.prototype.then.call` can throw for a branded Promise with a failing `@@species`; observer setup then did not attach, so the run is released immediately and the exact return value is preserved.
- `dispatch.js` `agentEvents.emit`: Cordis `emit` invokes callbacks through `Array.map` (`@freddie/cordis` `events.js`), so one synchronous throw starves later listeners and returned promises are discarded. Agent notifications are non-vetoing, so the same filtered callback set (`ctx.events.dispatch('emit', args)`) is resolved here and both failure modes are contained independently.
- `consumed-work.js` `foldConsumedWork`: a splice that inserts a replacement keeps the work pending under a new identity, so only a cancellation that leaves nothing inserted counts as `droppedUnrun`. A non-cancel splice with `removedCount` is a claim (the loop's own step-boundary read), always inside an open turn. When a turn closes with accounted work, drops recorded before it are that ending's own report; only a later drop is still unaccounted for (`droppedUnrun` resets).
