    Wire gm as a native Freddie tool via the existing MCP-client bridge
    
    An in-harness Freddie agent could only reach gm by shelling out via pwsh to
    hand-write and poll .gm/exec-spool files, since gm-mcp (the real MCP server
    exposing gm's spool dispatch cycle) had no path into the harness's own tool
    registry. freddie-mcp-client already provides exactly the bridge this needs
    -- the same mechanism examples/mcp-memory demonstrates for third-party MCP
    servers -- so this adds one disabled-by-default cordis.yml row (activates
    when GM_MCP_SERVER_PATH is set or a default ~/.gm-tools install is found)
    giving every in-harness agent a native mcp__gm__gm tool call, with zero code
    changes to gm or freddie-mcp-client. Live-verified: booted a real headless
    session with the row active, drove a turn that called mcp__gm__gm directly,
    and got back a real gm spool response.
    
    Resolved PRD rows:
    - wire-gm-mcp-as-first-class-freddie-plugin: Wire gm as a native mcp__gm__gm Freddie tool via the existing MCP-client bridge, live-verified end to end
