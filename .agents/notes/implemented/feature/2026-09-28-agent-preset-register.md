# Agent Note: runtime preset registration on `agentPresets`, and the deny-on-collision rule it carries

Status: implemented

## Problem

`deepseek-ai/deepseek-harness`'s `packages/preset/agent-preset` registers a preset at runtime: a `Group` plugin whose whole body is `yield await this.ctx.agentPresets.register(this.config)`, with `Config = { id, name?, description?, order?, plugins }`. Freddie's equivalent service (`packages/preset/agent-presets/src/index.js`) exposed an 11-method inventory and **no** `register`, so a preset could only come from a directory a configured root supplied. The sibling item `preset/agent-preset-registry` was deferred earlier; this note covers only the registration capability, on the existing service.

Upstream's registry answers a duplicate id by rejecting it (`Duplicate agent preset: ${id}`) and returns an async `unregister` disposer. That is the semantics to port, and it is also the fail-safe answer: a preset decides which tools and prompt sections an agent may use, so a registration that silently displaced an existing preset would change what an agent may do without anyone asking. Deny rather than allow.

## Decision

`ctx.agentPresets.register(definition)` on the existing service, in freddie's idiom.

**Conflict rule: reject, never displace — in both directions.** `register()` refuses an id another registration already holds (`PresetIdTakenError`, owner "declared by another plugin") and refuses an id any configured root supplies (owner "supplied by a configured preset root"). The read side mirrors it: `list()` appends declared presets after the discovered ones and skips a declared row whose id a root also supplies, warning once. Discovery re-reads the roots on every call, so a root that grows an id a registration claimed wins it from the next `list()` on rather than being layered over. Explicit and documented, because the alternative — a plugin narrowing a deployment's own compositions by claiming a name — is the exact hazard the rule exists to prevent. A registration's way out is always to pick an id no root supplies.

**Disposal: a preset never outlives its owner.** The registration installs `this.ctx.effect(() => withdraw, 'agentPresets.register(<id>)')`. A service method's `this.ctx` is rebound to the CALLER's context, so the effect lands on the fiber of the plugin that called `register` — unloading that plugin withdraws the preset, and a standing mount the preset already produced is disposed with it. The disposer `register()` returns does the same and is idempotent with the effect (guarded by a `withdrawn` flag and by record identity), so a plugin that yields it from its own `Service.init` and is then unloaded pays nothing twice. Should the effect itself throw — an unscoped caller — the definition is removed before the error propagates, so no half-registered row survives.

**Shape is validated at registration, the mount stays lazy.** `register()` runs the definition's rows through discovery's own `entryListProblem` (now exported) and refuses with `InvalidPresetDefinitionError`, so a declared composition is judged by exactly the check a file is — one derivation decides what an entry list is. It does NOT mount: freddie mounts lazily and single-flight, so a preset nobody selected costs nothing. A bad id is refused with `InvalidPresetIdError` by the same `PRESET_ID` a directory name must match.

**A declared preset mounts through the same audit as a written one.** `mount.js` gained `InlinePresetTree extends EntryTree` — `static inject = ['loader']`, the `EntryGroup.key` tree-carrier marker, a no-op `write()` (there is nothing to persist and no file to overwrite), and `Service.init` yielding `() => this.root.stop()` before `await this.root.update(this.config.rows)`. `mountPreset` picks it when `preset.rows !== undefined` and keeps `PresetTree` for a file, so every guard — an unscoped target, a row that never became usable, a service that leaked into the root realm — applies unchanged. Rows are `structuredClone`d at mount time: `EntryGroup.update()` mints an `id` into every row that names none, and baking those back into the array the declaring plugin still holds would be the same bug `applyEntryPatches` clones to avoid.

**Row resolution follows the declaring plugin.** Bare package names (and relative paths, there being no composition directory) resolve against the `baseUrl` the registration captured from its caller's context — the composition that plugin was loaded from, where its dependencies live. `importFrom` gained a `relativeBase` for exactly that: a written preset's relative row still resolves beside its own file.

**Registered presets are `trust: 'system'` and not writable.** `copy()` refuses ("it is declared by a plugin, which owns no directory to copy") and `remove()` refuses ("it is declared by a plugin; withdraw that registration instead"), so no roster surface can edit or delete one; editing it means editing the plugin. `trust` stays `system` rather than growing a third value, which keeps the existing Typert/wire enum closed and makes the api-proxy's "only a `user` preset may be removed" rule refuse a declared one on its own.

## Alternatives considered

**Last-writer-wins on a duplicate id.** Rejected, and this is the load-bearing rejection: a silently-shadowed preset changes an agent's capabilities without a deployment or a person having asked for it, which is worse than a refused registration. Saltzer & Schroeder's fail-safe default — deny when the policy is ambiguous.

**A separate `agent-preset-registry` package.** Rejected: this extends an existing service in place. Freddie's roster is one service with one `definitions` map; a second package would split the roster's ownership of an id across two services, and the duplicate check would have to reach across both — the deferral stands on its own merits (see below).

**Eager mount at registration, as upstream does.** Rejected: freddie's mount is lazy, single-flight, and stamp-refreshed per generation, and a declared preset has no stamp. Eagerly mounting would compose a subtree for a preset no session ever named. Shape validation at registration is the fail-early part of what eager mounting would have bought; the rest is a mount failure the session start already reports.

**Recording a bad definition as a broken roster row, the way discovery does for a file.** Rejected: `broken` exists so a person can see and delete the directory occupying an id. A definition is code a plugin author ships, has no directory, and no state to preserve for display; refusing it names the reason at the call site that can fix it.

**Letting a registration override a root-supplied id, since the plugin "owns" the name.** Rejected for the same reason as last-writer-wins, plus the explicit requirement: a runtime registration must never silently override a deployment-configured preset.

## Consequences

Verified live against the real stack — a real `Context` with a real `Loader` (`root.loader.builtins.group = Group`, exactly what `packages/boot/app-boot` installs at boot), a real `AgentPresets`, a real `createScope` agent, and a real shipped row (`@freddie/freddie-system-prompt` behind an `isolate: { systemPrompt: true }` group, as the shipped presets do it):

- **(a) resolves** — `list()` → `[{"id":"declared-demo","trust":"system","name":"Declared demo","description":"Registered at runtime by a plugin.","order":3}]`; `resolve()` the same; `read()` renders the rows in the loader dialect; `defaultId` `declared-demo`; `mount()` returns `declared-demo` with `composedPreset(agentCtx) === 'declared-demo'`; `livePresetMounts()` `["declared-demo"]`; `serviceForAgent(root, { ctx: agentCtx }, 'systemPrompt')` returns a live `SystemPrompt` — the declared composition really composed an agent, and the declaring plugin's own array is unchanged by the mount (`{"id":"system-prompt","name":"@freddie/freddie-system-prompt"}`, no minted ids).
- **(b) disposed with its owner** — after `fiber.dispose()` of the declaring plugin: `list()` `[]`, `livePresetMounts()` `[]`, `resolve('declared-demo')` throws `UnknownPresetError … (available: none)`, and `composedPreset(agentCtx)` is `undefined`. The freed id registers again; a second `withdraw()` is a no-op.
- **(c) the conflict rule** — `register({ id: 'declared-demo' })` → `PresetIdTakenError: … is already declared by another plugin …`; against a roster over the real `apps/cli/config/agent-presets` (`standard`, `code`, `minimal`, `cordis`), `register({ id: 'standard' })` → `PresetIdTakenError: … is already supplied by a configured preset root …` while a free id (`plugin-only`) is accepted and listed beside the four discovered ones. Refusals also covered: `Not An Id` → `InvalidPresetIdError`, `[{ nope: true }]` → `InvalidPresetDefinitionError: row 1 names no plugin`, `plugins: {}` → `the composition must be a top-level list of plugin rows`, `null` → `InvalidPresetIdError`, `remove()` and `copy()` → `PresetNotWritableError`.
- **No regression on the file path** — a discovered preset whose rows are a bare package, a `cordis:group` builtin, and a relative `./side.mjs` still mounts (`file-demo`), so the shared `importFrom` change keeps all three resolutions.

What this buys: a plugin can contribute a preset to the roster without a deployment shipping a directory, with the id ownership the deployment already had, and with the preset removed when the plugin goes. What it costs: one more way an id can be claimed (checked against two owners on every registration), a declared preset that no authoring surface can edit, and a mount failure that surfaces at the first session rather than at registration.

**The `agent-preset-registry` deferral is not re-opened by this.** Nothing found here is new evidence for it: the amenities that differentiate upstream's registry — Typert `@Remote` config exports, a `compositionInventory`, `acquireScope`, the settings-page configuration editor that persists a definition to disk — are still absent from freddie and were absent by choice. The one piece that was genuinely missing, runtime registration, is now on the service that already owns the roster.
