# Agent Note: open-in-app — resolved application catalog, icons, and launch endpoint as three webServer routes

Status: implemented

## Problem

freddie had no way to open the workspace directory in a *chosen* installed application. `codesearch` for `open-in-app` across the real tree returns zero matches outside the audit scratch dir, and freddie's `host/` group was only `apiproxy`, `directory-picker*`, `frontend-static`, `plugin-inventory`, `webserver`. What freddie has is `host.openPath` (`packages/host/apiproxy/src/api-proxy.js:1702`), which opens a path with the **OS-default** application — explicitly not this capability, whose subject is *which* application, with per-application resolution and launchers. `deepseek-ai/deepseek-harness`'s `packages/host/open-in-app` is exactly this: a fixed catalog of editors/IDEs, Git GUIs, terminals and file managers resolved to verified launchers on macOS/Windows/Linux, served as three HTTP routes.

## Decision

New package `packages/host/open-in-app` (`@freddie/freddie-host-open-in-app`), one Cordis function plugin registering three routes on `ctx.webServer`, ported from the upstream sources read off `raw.githubusercontent.com` (`src/catalog.ts`, `src/resolver.ts`, `src/icons.ts`, `src/index.ts`, `src/shared.ts`) plus the package README. The catalog table is ported verbatim — same 30 ids, same per-platform locator chain, same menu order — and resolution keeps upstream's proof discipline: every locator must yield an artifact the host actually holds, never a bare install record.

Adaptations, each forced by a real freddie difference rather than by preference:

1. **The trust fence is tighter than upstream's, and that is the headline adaptation.** dsh asks the composition's `connection` service for a rejection, which stacks a DNS-rebinding/origin fence on top of the deployment's browser authentication. freddie's connection README states its fence "is a reachability policy, not authentication" and that the Web carrier "provides no authentication layer" — so there is no browser authentication to lean on. Every route calls `isTrustedApiRequest(req, [])` with an EMPTY trust list, pinning it to loopback: the same pin `client-connection` applies to its `PRIVILEGED_METHODS` (`packages/client/connection/src/index.js:127`), `host.openPath` among them. Opening the workspace in a chosen application is that sibling host action's equal — both drive the operator's desktop from an HTTP request — so it takes the equal pin. The config deliberately carries **no** `trustedHosts` field; there is nothing to widen. Consequence: on a `0.0.0.0` deployment these routes are unreachable from the LAN, which is the intent.
2. **The connection service is not injected.** The fence is one pure request predicate, imported directly as `@freddie/freddie-client-connection/src/api-request-trust.js` (the parent-endorsed deep-import form), so `inject` is just `['webServer']` and mounting the package cannot deadlock on a service the route never uses.
3. **PATH names resolve in-process, not through `ctx.subprocess`.** Upstream calls `ctx.subprocess.resolveExecutable()`. freddie's seam resolves inside a provider's *execution world*, which for a remote provider is the sandbox — the wrong machine for a desktop application. `resolver.js` stats `PATH`/`PATHEXT` itself (no shell, no `which`), which also keeps the package from requiring a subprocess provider in the composition.
4. **The Linux desktop-entry and icon lookups are implemented here.** Upstream imports `desktopEntryFields`, `desktopDataDirectories`, and `desktopApplicationIcon` from `dsh-native-command`; freddie's `freddie-native-command` exports only `runNativeCommand`. The `[Desktop Entry]` parser, the XDG data-directory list, and the hicolor/pixmaps icon lookup are ~50 lines in `resolver.js` and `icons.js`.
5. **The shell-open verb is implemented here rather than imported.** Upstream routes the file managers through `dsh-native-command`'s `openNativePath`; freddie keeps that opener in `packages/host/apiproxy/src/native-path-opener.js`, and depending on the whole gateway for two functions was rejected (see Alternatives). `resolver.js` runs `open` (macOS), `powershell.exe Invoke-Item -LiteralPath` (Windows), or `xdg-open` (Linux) through `runNativeCommand`.
6. **One dependency beyond the parent's list: `@freddie/freddie-subprocess`, for `scrubbedParentEnv()` only.** Requirement 10 (launches must not pass inherited credentials) needs a scrub, and re-implementing its `/KEY|PASSWORD|SECRET|TOKEN/i` + `FREDDIE_*` rule locally would create a second definition of credential policy — worse than depending on the package that owns the one. It is a workspace-internal dependency; **no new npm dependency** is added.
7. **Upstream's injectable `OpenInAppInternals` seam is dropped.** It exists "for deterministic tests"; freddie ships no test files, and an injectable platform/run/launch/resolveExecutable seam with no production caller is exactly the unsupported public surface `packages/AGENTS.md` warns about. Resolution reads `process.platform` and the real environment directly, which also means the SSH guard reads the *inherited process layer* as specified rather than a supplied fact.
8. **The three deadlines become required-with-defaults** (`probeTimeoutMs` 10000, `iconTimeoutMs` 10000, `launchWatchMs` 1000) — freddie's `.default()` idiom, as `client-connection` uses — rather than upstream's three required fields with no defaults.
9. **`./shared` drops upstream's document-relative route forms** (`OPEN_IN_APP_*_ROUTE`) and keeps the three absolute paths plus JSDoc payload types. There is no browser surface reading them; a fourth unused constant would be an unsupported public export, and the README records the browser surface as deferred.
10. **`src/invariant.js` ships** because `packages/AGENTS.md` requires every package to own `./invariant`; it registers the manifest name and gives an empty installer with a package-specific reason (every fact is owned and checked where produced).

Name mapping: `@deepseek-ai/dsh-host-open-in-app` → `@freddie/freddie-host-open-in-app`, version `0.1.1-rc.2` to match the sibling host packages.

## Alternatives considered

**Ask `ctx.connection.requestRejection` (upstream's route) with a `trustedHosts` config field.** Rejected: freddie's fence is documented as a reachability policy, not authentication, so passing a deployment's trusted hosts would expose a desktop-launch endpoint to any LAN caller. `client-connection` already pins `host.openPath` to loopback for the same reason; consistency with the sibling host action decides it.

**Depend on `@freddie/freddie-host-apiproxy` for `openNativePath`/`canOpenNativePath`.** Rejected: a three-route leaf package depending on the whole API gateway inverts the layering and pulls the gateway's dependency closure in; the opener is ~12 lines and this package already needs `runNativeCommand` for `reg.exe`, `xcode-select`, `sips`, and the icon script. Cost: WSL translation (`wslpath -w` + the Windows shell) is not reproduced, so the Linux file-manager entry is not offered on WSL — recorded as deferred rather than silently claimed.

**Reuse `ctx.subprocess.resolveExecutable` (upstream's PATH resolver).** Rejected on correctness, not taste: the seam resolves in the provider's execution world, so a remote provider would search the sandbox for `code`/`zed`/`kitty` and report the operator's real editors as absent.

**Keep the internals seam so the macOS/Linux paths could be exercised.** Rejected: freddie ships no test files, and a seam with no production caller would be dead public surface. The Linux paths were instead exercised live against a real temporary XDG tree (Consequences).

**Implement the credential scrub locally to avoid the extra dependency.** Rejected: `scrubbedParentEnv` is freddie's single-sourced scrub definition; a second regex would drift from it silently, and drift in a credential policy is the one place duplication is not affordable.

## Consequences

Verified live on freddie's real stack — real `@freddie/cordis` `Context`, the real `WebServer` service on a real loopback socket, the plugin loaded with `ctx.plugin`, real `reg.exe`, real PowerShell `ExtractAssociatedIcon`, real detached launches — not stubs:

- **Resolution (real Windows 11 host, `resolveOpenInAppApps(10000)`, 7026 ms):** `resolvedCount=3` — `explorer` (fixed → `shell-open`, icon `C:\WINDOWS/explorer.exe`), `vscode` (`App Paths` → `C:\Program Files\Microsoft VS Code\Code.exe`), `gitbash` (Uninstall record "Git version …" → `C:\Program Files/Git/git-bash.exe`, args `["--cd={path}"]`).
- **Routes:** `GET /open-in-app/apps` → `200 {"apps":["explorer","vscode","gitbash"]}`; `GET /open-in-app/icon/vscode` → `200 image/png`, 1090 bytes of real PNG extracted from `Code.exe`; `GET /open-in-app/icon/does-not-exist` → `404 {"code":"not-found","message":"no icon for does-not-exist"}`; `GET /open-in-app/icon/cursor` (not installed) → `404`; `GET /open-in-app/open` → `405` with `Allow: POST`.
- **Fence:** the same apps request with `Host: evil.example.com` → `403 forbidden`; `POST /open-in-app/open` with that Host → `403 forbidden`.
- **Wire validation:** `content-type: text/plain` → `415`; body 65537 bytes → `413`, 65536 bytes → `200` (boundary is exact); relative path → `400 path must be an absolute directory path`; a path naming a file → `404 directory does not exist: …`; unknown app id → `400 unknown or unavailable app: nope`.
- **Launch:** `POST` with `app=explorer` and `app=gitbash` on `C:\dev\freddie` each returned `200 {"ok":true}` and really opened the application. `launchResolved` classified a vanished executable as `missing`, `cmd /c exit 0` as `launched`, and `cmd /c exit 3` as `failed`.
- **SSH guard:** with `SSH_CONNECTION` set in the process environment, `GET apps` → `{"apps":[]}`, `POST open` → `400 unknown or unavailable app: explorer`, `GET icon/vscode` → `404`.
- **Disposal:** disposing the plugin fiber left `GET /open-in-app/apps` answering `404`, so the registrations really are cordis effects.
- **Linux paths** (against a real temporary XDG tree with `process.platform` overridden, the only way to reach them from this Windows host): `resolvedCount=5` — `filemanager` (`xdg-open` via PATH, `DISPLAY` set), `vscode` and `zed` (`cli` locator, real PATH hits), `kitty` (desktop entry with an absolute `TryExec` → the real file), `gnometerminal` (desktop entry with a bare `Exec` resolved through PATH). Icons: `kitty` → `image/png` (hicolor 64x64), `gnometerminal` → `image/svg+xml` (hicolor SVG), `filemanager` → `null` (no desktop entry, so the route would answer 404).
- **`pnpm run publint`** (run as `node scripts/publint-all.js`, 259 packages): `All good!` for `packages/host/open-in-app`. Two workspace packages fail — `packages/api/terminal-controller` (declares `./client`, `./typert`, `./remote` exports whose files do not exist) and `packages/llm/llm-pi-ai`. Both are **untracked in-flight work by sibling agents**, neither is touched by this change, and `git_status` confirms it.

Consumers read the three routes directly; a browser surface is additive client work and is deliberately not part of this change. Cost: one resolution pass (~1.4 s per `reg.exe` root on Windows, once per process) before the first apps or icon response, and the routes' LAN unreachability that consequence 1 makes intentional.
