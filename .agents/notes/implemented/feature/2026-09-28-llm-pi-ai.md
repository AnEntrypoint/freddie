# Agent Note: pi-ai multi-provider LLM adapter (`@freddie/freddie-llm-pi-ai`)

Status: implemented

## Problem

freddie's LLM plane ships the seam (`packages/llm/llm`), one real adapter family
(`packages/llm/llm-deepseek`), `llm-retry`, and `token-meter`. It had no adapter for pi-ai, so
every provider pi-ai reaches — OpenAI, Anthropic, Google, Groq, Cerebras, Fireworks, Baseten,
Cloudflare, z.ai, and the rest of its 39-entry built-in catalog — was unreachable from freddie
without writing one adapter per vendor.

dsh's `packages/llm/llm-pi-ai` is the generic answer: one plugin instance, one provider per
configured route, three wire protocols, and a single streaming event vocabulary.

## Decision

Port it as `packages/llm/llm-pi-ai` (`@freddie/freddie-llm-pi-ai`), written from
`deepseek-ai/deepseek-harness`'s `packages/llm/llm-pi-ai/src/*.ts` read off raw.githubusercontent.com.
Buildless plain JavaScript with JSDoc types, no build step, no new framework.

- `src/index.js` — cordis plugin (`name = 'llm-pi-ai'`, `inject = ['llm']`): profile resolution,
  configurable-provider directory, model-discovery offer, adapter registration, authorization-flow
  registration, and the user-settings section.
- `src/adapter.js` — `PiAiAdapter extends LlmAdapter`. One immutable snapshot per resolution
  (profiles + pi-ai `Models` collection), captured before the first `await`, so a configuration
  change cannot reach a request already in flight.
- `src/config.js` — schemastery `Config` plus `resolveProfiles()` and `assertServiceable()`.
- `src/catalog.js` — the pi-ai catalog surface: providers, models, compat gates, and
  `resolveRouteModels()`.
- `src/provider.js` — builds the pi-ai `Provider` for one route (catalog reuse, or a static
  provider over one of three lazily loaded protocol implementations).
- `src/models.js` — `createModels()`, `createProvider()`, `getSupportedThinkingLevels()`.
- `src/context.js` — harness history → pi-ai `Context`, including durable images.
- `src/stream.js` — pi-ai events → harness stream chunks, plus terminal-failure classification.
- `src/replay.js` — durable replay metadata and assistant-history reconstruction.
- `src/auth.js` — the credential-store and auth-context adapters over `ctx.credentials`.
- `src/discovery.js` — "which models does this endpoint advertise?" over the wire or from the
  catalog.
- `src/login.js` — authorization flows for the catalog providers that ship a login.
- `src/invariant.js` — the companion every freddie package owes. `install` is deliberately empty:
  there is no runtime invariant this seam can assert without duplicating `ctx.llm`'s own registry
  truth.

Adaptations, each forced by a freddie fact rather than by preference:

- **No `resolveImageAttachmentAccess`, so no `resolveImageAccess` hook at all.** dsh bridges one
  attachment reference into the model-tool execution world through
  `ctx.fs.processPathFromHostPath`. freddie's `llm` seam exports no such resolver, and
  `requestImageHandleText(version)` takes one argument. The hook and its peer dependency
  `@freddie/freddie-attachment-local` are dropped; the attachment service alone supplies request
  versions.
- **No `requestImageDimensions`; the image policy is `{ maxPixels, maxBytes }`.** freddie's
  `attachments.readImageRequest(ref, policy, signal)` takes the route budgets directly, so dsh's
  `PiImageRequestBudget` → `requestImageTarget` translation disappears and `requestImagePolicy`
  is passed through unchanged.
- **Image offload is freddie's deterministic projection, not dsh's count-and-fail.** dsh computes
  an offload count, refuses with `IMAGE_OFFLOAD_REQUIRED_CODE` when it exceeds what the request
  allows, and runs a second projection step. freddie has no
  `requiredImageOffload`/`IMAGE_OFFLOAD_REQUIRED_CODE`/`projectOffloadedImages`; it has
  `offloadRequestImagesWithPolicy(messages, { representation: 'base64', maxBytes, byteQuantum: 1, byteLength })`,
  which replaces the oldest images with a text placeholder itself. Because offloaded images
  *become* `text` blocks, no second projection and no `offloaded` flag are needed — one call, then
  convert.
- **One harness user message becomes several pi-ai messages.** freddie has no `tool` role and no
  `developer` role; tool results are `tool-result` blocks nested inside *user* messages. Conversion
  therefore flushes accumulated text and image content into a pi-ai `user` message before each
  `tool-result`, which becomes its own `toolResult` message carrying the tool name recorded from
  the preceding assistant tool call. `assertSupportedHistory` shrinks accordingly: only images
  outside user messages are refused.
- **`brandString<ToolCallId>` → `CallId`.** freddie brand-constructors are `CallId` and
  `ReasoningEffortId`; `ReasoningEffortId(level)` is unchanged.
- **Settings install replaces dsh's volatile-config machinery.** dsh uses `Volatile`,
  `internal/config`, `loader/volatile-update`, and `settings.configure({ auto: false })`. freddie
  has none of those; the equivalent is
  `installSettingsSection(ctx, NS, Config, config, { setSource, onChange, validate })` with
  `NS = settingsNamespace('llm-pi-ai')`. `validate` runs `assertServiceable` over the candidate,
  which is the freddie analogue of dsh's `internal/config` rejection. Because `scope.get()` hands
  back a fresh object per read, profile memoization compares by `deepEqualJson` (from
  `@freddie/freddie-settings`, llm-deepseek's import) rather than by identity — the resolved map's
  identity is what the adapter keys its provider collection on, so a deep-equal snapshot must
  return the same one.
- **Discovery takes one argument.** freddie's `registerModelDiscovery(settingsNs, discover)`
  invokes `discover(request)` with a single argument and `signal` riding on the request; dsh's
  passes `(request, signal)`. The stored-profile thunk is unchanged.
- **Directory entries drop `error`, keep `declared`.** freddie's `LlmConfigurableProvider` has no
  `error` field; the catalog diagnostic stays on the resolved profile and surfaces through
  `modelOf()` as `INVALID_CONFIG` instead.
- **`api: 'dsh-foreign'` → `api: 'freddie-foreign'`** in `foreignAssistant`.
- **Authorization needs no explicit commit.** freddie's seam confirms a flow by observing
  `credentials/record-updated` for the flow's key, and `credentials.modifyRecord` fans that event
  out (`packages/credentials/credentials/src/index.js:251`). pi-ai writes through the store this
  package hands it, at exactly `recordKeyFor(providerId)`, so the write is witnessed without the
  flow committing anything itself.
- **`using watchdog = idleWatchdog(...)` is native freddie style**, not a port artifact — see
  `packages/llm/llm-deepseek/src/adapter.js:320`.

## Verification

Run against real code on freddie's real stack (Node v24.15.0), no test files written.

- pi-ai catalog: `catalogProviderIds()` → 39 ids; `catalogProvider('openai')` →
  `{"id":"openai","name":"OpenAI","baseUrl":"https://api.openai.com/v1","auth":["apiKey"]}`;
  `catalogModels('openai')` → 39 models, `gpt-4` on `openai-responses`.
- `resolveProfiles()` over a catalog route and a hand-declared route: both produced a
  `piProvider`, resolved retry policy, and `configuredMaxTokens` `[["acme-large",4096]]`.
- `createModels()` + `setProvider()` + `getModel()`: known ids resolve, unknown returns
  `undefined`.
- Stream parsing (`toStreamChunks`) over a full thinking/text/tool-call turn → `block-start`,
  deltas, `block-end`, `usage`, `finish { kind: 'tool-calls' }` with a `pi-ai` v2 replay envelope.
- Error mapping, each through a real terminal `error` event: `429` → `RATE_LIMIT`, `401` → `AUTH`,
  `413` → `INVALID_REQUEST`, `500` → `SERVER`, timeout wording → `TIMEOUT`, `other side closed` →
  `TRANSPORT`, context-overflow wording → `CONTEXT_WINDOW_EXCEEDED`, unrecognized → `PI_AI_ERROR`;
  an aborted caller signal → `kind: 'aborted'`; a contentless `stop` → `EMPTY_RESPONSE`.
- Context conversion: a system message became `systemPrompt`, and one user message carrying text,
  a tool result, and trailing text became `user` → `toolResult{toolCallId, toolName: 'bash'}` →
  `user`, preserving order.
- Image path: under an 8-byte base64 bound the oldest image became freddie's
  `[image omitted to keep the request within its image limit; …]` placeholder and the newer one
  stayed as `{ data: 'iVBORw==', mimeType: 'image/png' }` beside `Image sha256:bbb; request image
  2x2px.`; a text-only conversion refuses an image, and an image in assistant history is refused.
- **Live round trip.** A local OpenAI-compatible HTTP endpoint on 127.0.0.1: discovery read
  `GET /v1/models` and returned `local-model` (8192/1024) and `local-vision` (32768/4096), dropping
  an empty id and a non-object row. `prepareCall` then streamed a real SSE response into
  `block-start` → two `text-delta` → `block-start tool-call` → two `tool-call-delta` with
  `id: 'call_1', name: 'bash'` → `block-end` ×2 → `usage { inputTokens: 5, outputTokens: 9,
  totalTokens: 14 }` → `finish { kind: 'tool-calls' }` with `responseId: 'chatcmpl-1'`. The server
  recorded the request body our adapter produced: `model`, `messages`, `stream`, `stream_options`,
  `store: false`, `max_completion_tokens: 1024`, `temperature: 0.25`, and the `bash` tool schema.
  A 401 endpoint produced `finish { kind: 'error', failure: { code: 'AUTH' } }`; a 400
  context-length endpoint produced `CONTEXT_WINDOW_EXCEEDED`. Unknown model → `UNKNOWN_MODEL`,
  unowned route → `NO_ADAPTER`, unsupported effort → `UNSUPPORTED_REASONING_EFFORT`.
- `pnpm run publint`: exit 0, 269 packages, 269 × `All good!`, including
  `packages\llm\llm-pi-ai`.

### Not proven

- **No round trip against a real third-party provider.** No credential or reachable vendor
  endpoint exists in this environment. What is proven is request shaping, stream parsing,
  error mapping, and the full `prepareCall`/`stream` path against a real HTTP endpoint speaking
  the same wire protocol; what is unproven is each vendor's own endpoint quirks and its auth
  handshake.
- **OAuth/device-code login.** No catalog provider's interactive login was run; pi-ai's
  `AuthInteraction` translation is typed to the union pi-ai exports and was not exercised against
  a live authorization server.
- **The durable attachment service.** Image request versions were resolved through a local object
  satisfying `readImageRequest` and returning a `RequestImageAttachment`-shaped value; freddie's
  real `offloadRequestImagesWithPolicy` and `requestImageHandleText` did the rest. Booting
  `freddie-attachment-local` needs `FREDDIE_HOME` and its compression limiter, which this
  verification did not stand up.
- **Compat-gate and thinking-budget fields**, and the websocket transports, are configuration
  surface only here: they were validated by the schema and by catalog resolution, not by a
  provider that exercises them.

## Alternatives considered

**Ship nothing and add providers one adapter at a time.** Rejected: it is 39 times the work for a
strictly narrower result, and the seam already has exactly one place a generic adapter belongs.

**Port pi-ai's model registry into freddie instead of depending on the library.** Rejected: the
registry is generated data with its own refresh pipeline, and a fork of it would drift silently.
