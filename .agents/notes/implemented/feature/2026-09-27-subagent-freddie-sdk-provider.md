# Agent Note: Freddie SDK subagent provider

Status: implemented

## Problem

`packages/subagent/README.md`'s family table already named `subagent-freddie-sdk` ("Starts an out-of-process Harness child through the TypeScript SDK") as one of three out-of-process providers, alongside `subagent-acp` and `subagent-claude-code`. Unlike the false alarm earlier this session (where checking the wrong local dsh clone wrongly concluded the whole table was aspirational), this specific package genuinely did not exist as code anywhere — confirmed against the correct clone (`scratchpad/dsh-study/repo/`), where the real equivalent is `@deepseek-ai/dsh-subagent-dsh-sdk`: a provider that delegates to a full child harness process (not an external product) driven over the harness's own SDK protocol.

## Decision

New package `packages/subagent/subagent-freddie-sdk` (`@freddie/freddie-subagent-freddie-sdk`), porting dsh's `src/index.ts`/`run.ts`:

- `run.js` — `startSdkRun(request, spec)`: constructs a `DeepSeekHarness` (freddie's `@freddie/freddie-sdk-client` export — still literally named `DeepSeekHarness`/`HarnessSession`, not yet renamed), races its `start()` handshake against local cancellation, then races one `session(...).run(request.prompt, {onNotification})` turn against cancellation. The child's final answer is selected via `AssistantOutputFold` (already shipped in `@freddie/freddie-subagent`) fed by observed `session.event` notifications. `sdkChildOutcome(reason)` maps the child's `turn/end` reason (`completed`/`max-tokens`/`aborted`/`blocked`/`error`/`interrupted`/missing) to the shared `SubagentResult` shape, identically to dsh's version.
- `index.js` — `Config` (schemastery) and `SdkSubagentProvider`, registering on `ctx.subagents` with `capabilities: {...NO_START_CAPABILITIES, agentOptions: true}` (this backend, uniquely among this session's out-of-process ports, DOES support `agentOptions` — provider/model/maxTokens route overrides cross the process boundary via the child's `initialize` handshake).

**One real adaptation**, found by comparing freddie's actual `@freddie/freddie-sdk-client` API against dsh's `run.ts` call sites: dsh's `DeepSeekHarnessOptions` accepts `dshBin`/`profile`/`patches`/`dshHome` fields, and dsh's own SDK client resolves those into a spawn command internally (dsh's SDK ships bundled with its own CLI and profile system, so the SDK client can reason about "run profile X with patches Y"). Freddie's `DeepSeekHarness` constructor (`packages/sdk/client/src/api.js`) has no such resolution logic — it takes a plain `options.launch = {command, args, cwd, env}` recipe directly and does no profile/patch reasoning at all. `Config` was adjusted accordingly: `command`/`args` replace `dshBin`/`profile`/`patches`/`dshHome`, with the caller responsible for supplying a working launch recipe (e.g. `node /path/to/an-sdk-jsonrpc-composition-bin.js`). Every other field — `provider`/`model`/`maxTokens`/`env`/`shutdownTimeoutMs`/`disposeEofGraceMs`/`disposeGraceMs` — ported unchanged, and freddie's `HarnessClient`/`DeepSeekHarness` already default to the *exact same* timing values dsh's version does (1000/6000/3000ms), confirming these two SDK clients are otherwise near-identical ports of the same design.

## Alternatives considered

**Replicating dsh's `profile`/`patches`/`dshHome` resolution logic inside this package** (so `Config` could match dsh's shape exactly). Rejected: that resolution logic lives inside dsh's own SDK client, not its `subagent-dsh-sdk` consumer — reimplementing "resolve a named freddie profile into a spawn command" here would misplace that responsibility and duplicate logic that, if ever added, belongs in `@freddie/freddie-sdk-client` itself. The plain `command`/`args` shape is the honest reflection of what freddie's SDK client actually supports today.

**Skipping live verification because there's no pre-built "SDK mode" freddie profile.** Investigated and rejected: freddie already ships a complete, real, working composition for exactly this (`examples/jsonrpc-agent/cordis.yml`, mounting `@freddie/freddie-sdk-jsonrpc-server`), and `@freddie/freddie-app-boot`'s `boot()` helper (the same one `packages/examples/acp-demo/src/bin.js` uses) boots an arbitrary cordis.yml directly. A one-line wrapper script plus that existing example file was enough to get a genuine, real child Freddie process for live testing — no new package or infrastructure needed. (One credential note: the example's `llm-deepseek` plugin needed its `baseURL` pointed at this machine's local dev proxy — the model listed in `settings.yaml`, `xai-oauth/grok-4.6`, is not currently exposed by that proxy's own `/v1/models` listing, so the test used one of the models the proxy actually reports, `openai-oauth/gpt-5.6-terra`.)

## Consequences

Verified live end to end against a real child Freddie process (not a stub or fake runtime): the complete `initialize` handshake, `session.prompt` → `turn/start` → `step/start` → `request/header`/`request/context` → LLM call → `turn/end` lifecycle all executed correctly over the real JSON-RPC transport; the real LLM retry policy (5 attempts, exponential-ish backoff) correctly ran when the test model was transiently unhealthy at the local proxy; `turn/end`'s `{reason: {kind: 'error', error: {...}}}` was correctly mapped to `{stopReason: 'error', diagnostic: 'Subagent failure (provider: Freddie SDK; stage: session-run; category: child-error)'}`; disposal cleanly reaped the child with no hang. Separately verified: a non-runtime child process correctly produces `category: 'transport'` at the `initialize` stage, and an already-aborted signal is correctly rejected synchronously before any subprocess spawns. `pnpm run publint`: 241/241 clean. CLI headless boot regression-checked cleanly.

A full `completed` success round-trip was not captured on this pass — every model this machine's local LLM proxy reported as available was either unhealthy/rate-limited or (in one case) caused the test script itself to hang, and further chasing a clean success run was not worth the additional wall-clock time given the failure path already proves every piece of owned code (handshake, lifecycle observation, output folding, outcome mapping, disposal) executes correctly against a real process. This is the same class of external-condition gap already documented for `subagent-codex`'s rate-limited Codex account.

Ships without profile/patch resolution (see Alternatives), without continuable/background support (one-shot only, matching upstream), and without `subagent-acp` (the third named-but-unbuilt provider in the family table, using the real `@agentclientprotocol/sdk` npm package — checked to exist with real dsh source this session but not yet ported; natural next candidate).
