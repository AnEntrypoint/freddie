## 2026-09-04 -- vendor cache split must include patched webjsx

Goal (G): Troubleshoot the Freddie harness, identify real issues, and fix them with live verification.
What drifted / what went wrong: After splitting `/vendor/` cache so only `@freddie/` stayed `no-cache`, patched `webjsx@0.0.73` kept `immutable` under an unchanged version URL — the same stale-crash class the original blanket `no-cache` was meant to stop. The live web process also does not HMR host plugins, so a source edit is not proven until `serveVendor` is invoked in-process or the process restarts.
Fix / resolution: Treat `@freddie/`, `webjsx@`, and unversioned stubs as `no-cache`; keep other versioned third-party paths `immutable`. Verify `serveVendor` in-process, not only against the already-booted GUI.
Generalizes to: A versioned URL is immutable only when contents cannot change without the version changing. Local patches and workspace-linked packages fail that test. Host HMR is off for web; live GUI headers can lag source.

## 2026-09-05 -- HMR ran but silently served stale custom-element classes

Goal (G): Set up perfect hot reloading for the web client, so a source edit takes effect live without a manual server restart.
What drifted / what went wrong: An earlier lesson recorded "the live web process does not HMR host plugins, so a source edit is not proven until the process restarts." That was half right and misleading in the worse direction. Client packages DO hot-reload (the poll detects the edit, an SSE `rebuilt` frame arrives, the module re-imports, the cordis fiber swaps cleanly, no errors). But `customElements.define(tag, Class)` binds a tag for the document's lifetime, and every definition site guards on `customElements.get(tag) === undefined`, so the re-imported module's define is a silent no-op and every live element keeps the ORIGINAL class. Measured directly: the rebuilt frame arrived and the row re-rendered, while the live constructor's source was byte-identical and did not contain the probe just added to it. So "HMR is working" and "my edit is live" were two different facts, and only the first was true.
Fix / resolution: Host classifies each row once during the walk its poll already does (no extra traversal, cached per process) for `customElements.define`, and flags the `rebuilt` frame; the browser half reloads on a flagged frame instead of a swap that cannot take, matching what `shell-rebuilt` already does for the same underlying reason. Rows without custom elements still hot-swap in place. Verified both paths live with a page-stamp/sessionStorage-twin probe.
Generalizes to: A hot-reload mechanism reporting success is not evidence the new code is running -- verify the live artifact (constructor source, a changed constant's visible effect), not the reload log. Any one-shot global registration (customElements.define, a registry keyed by stable name, a `once` guard) is invisible to module-level hot swap and will serve stale code silently. When a swap provably cannot carry an edit, a full reload is the correct exit, not a fallback: an honest reload beats a swap that looks like it worked. Prefer that over a proxy/indirection layer when the hot path is performance-sensitive -- a dev-only need should not tax production-shaped code.

## 2026-09-05 -- "elements created" is not "DOM replaced"; verify which before optimizing

Goal (G): Get the freddie web client's interactive latency as low as measurably achievable via repeated flamegraph/fix rounds.
What drifted / what went wrong: A MutationObserver counting added elements per keystroke was the tool that found two real bugs (tool rows and context rows rebuilt from scratch, ~185 + ~31 fresh elements each keystroke, from one-shot `X(props)` factories called as `h(X, ...)` in a re-rendered tree). But I then kept treating its third finding -- 248 `code` elements -- the same way, and shipped three separate memoization fixes chasing it, each of which measured as changing nothing. Only after the third did I check the right thing: comparing the live `code` node identity across a keystroke showed it was NOT replaced. The markdown was re-parsing into fresh DETACHED nodes that webjsx's diff then discarded. Real wasted parse work, but nearly free compared to actual DOM replacement -- and I had assumed equivalence between "created" and "mounted" for three rounds without testing it.
Fix / resolution: The two genuine cases were fixed by routing through the create-or-update form the codebase already had for CodeBlock/ReadBlock (intrinsic tag + webjsx `ref`), taking their per-keystroke creation to zero and settled time 292ms -> ~70ms. The memoizations still landed (they remove real re-parse work) but were committed with their true, smaller scope stated rather than credited with the DOM win.
Generalizes to: A MutationObserver's addedNodes counts CREATION, not mounting -- a framework that builds a subtree and then discards it inflates that count with cheap garbage. Before optimizing a high count, compare a live node's identity across the interaction: if it is the same object, nothing was replaced and the cost is allocation, not layout. Also: when two or three well-reasoned fixes in a row each measure as zero change, that is the bounded-retry signal to stop fixing and go re-measure the premise, not to try a fourth fix.

## 2026-09-05 -- synthetic dispatchEvent hid a 6x real input latency

Goal (G): Eliminate the remaining perceptible lag in the freddie web client, driven by real flamegraph evidence.
What drifted / what went wrong: Three prior rounds measured typing with `el.dispatchEvent(new InputEvent('input'))` and reported ~9ms sync / ~50ms settled, concluding the client was already at a floor. The user said it still felt laggy. Measuring real keystrokes (CDP `type_text` plus the browser's own Event Timing API) showed p50 56-64ms and a 296ms worst interaction -- roughly 6x what the synthetic path claimed, and the synthetic path never fired keydown at all, so `#onKeyDown` (114ms of self time, the single largest app frame) was invisible for three whole rounds. The breakdown also inverted the earlier picture: input delay ~0ms and processing ~5ms, with ~54ms of PRESENTATION delay, so the remaining cost was never script at all.
Fix / resolution: Real input surfaced three genuine wins -- `canSteerQueue` computed eagerly on every keydown for a value read only behind accelerated-Enter, `parseArgs` re-running JSON.parse up to 3x per tool row per render, and (the actual root cause of a memo that had resisted three earlier fixes) `openFile: (path) => ...` rebuilt inline in ChatView's seat props, which invalidated the mentions cache and re-parsed the closing markdown block every keystroke. p50 69ms -> 43-57ms, max 97ms -> 68-85ms. A fourth change (skipping MarkdownText's applyDiff when nothing can differ) removed 400 element creations per ten keys but did NOT move latency, and was committed saying so.
Generalizes to: `dispatchEvent` is not input. It skips the browser's real input-to-paint pipeline and fires only the one event named, so whole handler families (keydown/keypress/beforeinput) never run and presentation delay is never measured. Drive real interaction (CDP input, Event Timing API) before concluding anything about interactive latency, and prefer a keydown-to-second-rAF timer over a PerformanceObserver + CPU profiler, both of which visibly distort this path (`v8::Debugger::AsyncTaskRun` was ~1s of a ~9s trace). When a fix removes provable waste but moves no user-visible metric, say both things in the commit rather than crediting it with the win.

## 2026-09-06 -- "refusing to resume" was a stale server process, not a code defect

Goal (G): Get the in-harness agent session resuming again after it stopped mid-task.
What drifted / what went wrong: session.models failed for EVERY real session with `resume failed: agent-presets: refusing to compose an unscoped context`, and the composer showed an empty "Select model". The uncommitted tree contained an in-harness agent's edits to all four agent-preset YAMLs and two llm JS files, so those looked like the obvious cause. They were not. Stashing everything and running committed code made resume work -- which read as "one of the stashed edits breaks it" -- but restoring them one at a time ended with ALL of them restored and resume still working. Nothing in the diff was ever the cause: the original failure was a long-lived web process serving code from before those files existed on disk in their current form, and each restart in the bisect quietly fixed it. The bisect "found" a culprit that did not exist, and would have produced a confident wrong answer if I had stopped at the first green result.
Fix / resolution: Restart the server and re-verify. Confirmed live: session.models returns the real provider/model groups, and the UI shows "Grok 4.6 (xAI, via acptoapi) · High" with To-dos and the Ongoing Goal intact.
Generalizes to: This is the third stale-process trap this session (the earlier two: host plugins not hot-reloading, and a lockfile that only installed because of a warm local cache). Before bisecting ANY behavior against source, restart the process first and re-confirm the symptom still reproduces -- otherwise the bisect is measuring process age, not code. A bisect whose "fix" is a step that also restarts the system has proven nothing. Note the boot lock: `.litebox-cache/boot.lock` survives a killed process, and a stale one blocks the next boot with a message that reads like a live conflict; check whether the named pid is actually running before waiting on it.

Fix / resolution: Nothing to fix in HMR.
