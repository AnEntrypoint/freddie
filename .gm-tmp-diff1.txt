    fix(security): add path traversal validation to credential_files tool
    
    The credential_files tool accepted a 'name' parameter from the LLM that
    flowed unchecked to FileAuthStore._path(), which calls path.join(authRoot, name)
    with zero containment. Implement defense-in-depth:
    
    1. Tool handler entry validation: name must match SAFE_NAME regex
       (letters/digits/dash/underscore only). Reject invalid names with a clear
       error message, never attempt to sanitize -- any name failing this check
       is operator error or an attack, not a legitimate input to be "fixed".
    
    2. FileAuthStore._path() containment assertion: verify that the resolved
       path stays within the auth directory. This catches logic errors or future
       refactors that skip the validation layer.
    
    Validation at the tool handler entry level follows the precedent established
    in plugins/core/skills-hub/lib/skills_hub.js, ensuring consistent security
    posture across credential/skill management surfaces.
    
    All path traversal attempts are blocked at the validation layer:
      - '..' and '.' rejected
      - absolute paths (/, /etc/passwd) rejected
      - traversal sequences ('../../../etc/passwd') rejected
      - both Unix and Windows path separators handled
    
    Tested via exec_js with 10 edge cases covering both valid credentials and
    all major traversal attack classes. Full-stack verification confirms:
      - Valid credentials pass through (anthropic, OPENAI_API_KEY, my-cred-123)
      - All path traversal attempts fail with clear error messages
      - Defense-in-depth containment check provides secondary safeguard
