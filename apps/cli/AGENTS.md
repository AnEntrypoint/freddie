# AGENTS.md — freddie CLI

## Rationale

Agent presets (`config/agent-presets/<id>/agent.cordis.yml`; persona `{{model}}` / `{{cwd}}` resolve from the agent's own route and workspace):

- The `cordis` preset is the standard coding agent plus the ability to read and write the runtime it runs in (`tool-cordis`, the `editing-cordis-compositions` skill). `scripts/rescope-vendor.js` POSTCONDITIONS pin two strings in its `agent.cordis.yml` so the upstream `cordis` names survive the rescope: `a plugin row in a \`cordis.yml\`` and `corrupting the \`cordis\` preset`; change the persona text and those pins together.
- Planes: presets are AGENT-PLANE compositions. `standard` mounts once per process under a standing scope and sessions join by scope parentage; `code` and `cordis` mount under one agent's scope, so their tools and prompt sections belong to that session alone. The host composition (`packages/bundle/base` plus web) keeps the registries, sandbox and approval stack, persistence, and the model route.
- Realm rule: every service row must sit in a group carrying an `isolate` realm. Without one it publishes into the root realm, where it is process-global (presets collide, host readers resolve one preset's instance for every session); `freddie-agent-presets` rejects that at mount. `isolate: {name: true}` is an entry-local realm, one private instance per mounted preset. A shared label does not pool instances: `provide()` throws on the second registration under the same realm symbol.
- Host-plane rows a preset only chooses to use (no realm needed): `tool-fs` / `tool-fs-search` (register into the host `tools` registry and provide nothing; the `fs` service and policy stay on the host); `skill-filesystem` / `tool-skill` (register into this preset's layer of the per-scope skill registry; the merged catalog also carries globally registered repository plugins); `tool-web` (the `web` service and its providers stay on the host).
- `shell-env` stays on the host: `packages/bundle/web-app` injects it to publish `FREDDIE_WEB_URL`, and a host row that injects a service must be host-plane because injection resolves before any session exists. Behind a preset realm the variable never reached the model's shell. The bash/pwsh executors are host-plane too.
- `tool-jobs`: the task registry (`jobs`) stays on the host. Its producers sit outside any realm a preset could give it, `tool-bash` resolves it with `ctx.get`, and an entry-local realm is invisible to sibling rows, so `run_in_background` would report background jobs unavailable while the controls sat in the catalog. It is keyed by owning agent, so one host instance serves every session.
- `tool-goal`: the goal service, session driver and `/goal` command stay on the host; the Gateway serves the goal domain as Remote endpoints whose receiver comes from a generated descriptor that resolves `goals` on the host, so an entry-local realm would hide it. Keyed by session.
- `tokenMeter` stays on the host: no configuration, folds keyed by Session, and it owns the context-meter projection units the browser reads for every session (behind a realm they would come and go with whichever presets are mounted). The `compaction` group instead owns a realm because `compaction-basic` reads `toolResultPrune` through `ctx.get`, so the pruner must share it.
- `time-context`, `tmux-context`, `tool-session-query` (`standard`, `code`, `cordis`; never `minimal`): host-plane-style rows that register a pre-step listener or tools into the host registries and provide nothing, so no realm is needed. They are default-on, and the Web bundle disables the same-id base rows so each agent gets one copy through its preset; `minimal` mounts none, which keeps its request a fixed prompt. The browser provider is the exception: its exclusive `browser-use` slot registers once per process, so it stays a host row and skips agents by preset id (`excludePresets: [minimal]`).
- `planning` (`planMode`) is entry-local by nature: plan state is per-agent.
- `delegation` (`workflowEngine`): nothing outside an agent reads `workflows`, so every row reaching it shares one entry-local realm, and a consumer left outside would resolve an unpopulated host registry. The `subagents` registry and spawn/fork backends stay on the host (a process singleton whose cross-session queries the api-proxy serves to the browser; a provider name registers once). `tool-subagent-report` is host-plane for the same reason: it registers a continuable setup on that singleton and the setup list is not scope-aware, so one copy per mounted preset would register `report` once per live session and throw on the second.
- `code`: `standard` unchanged plus the `tool-presentation` row (`mode: code`): the model writes a TypeScript program against a generated SDK and `run_code` executes it, so several round trips become one. The registry stays on the host (the loop scheduler and API proxy presenters consume it); the preset owns only this agent's presentation. The row waits for the host's `codeRuntime`, so a deployment without a TypeScript runtime fails this preset at mount naming the id, not at the first request.
- `cordis`: `standard` plus the self-referential `tool-cordis` toolset, a composition-authoring skill and a persona saying which plane an edit belongs to. TRUST: `cordis_mount` evaluates model-written JavaScript against the live runtime and a composition it writes becomes a preset other sessions mount, so treat a session on this preset as shell access (the toolset is a trust boundary, not a sandbox). The skill ships inside the preset (it documents this deployment's two planes, and a preset is the unit that gets copied and edited); `baseUrl` is the preset directory, so its `skills/` root resolves wherever the preset is installed.
- `minimal`: the persona is the complete system prompt, so global identity, Web orientation, tool guidance and later assembly listeners cannot add prompt text; runtime context snapshots are suppressed; compaction is absent. The PTY registry is agent-owned (entry-local realm) but still consumes the host sandbox policy and subprocess implementation; exactly one shell stack mounts per host (bash gates off win32, pwsh gates off POSIX). The bare local filesystem shadows the host's sandboxed provider only for this preset, and the editor sharing that realm requires absolute paths.

## Launcher

- Launcher flags (`--profile`, `--patch`, config dumps) come first; the first unrecognized token starts the inner arguments, passed verbatim to the tree via `ctx.cmdlineArgs`. `--patch` is a single-value repeatable collector, never variadic (variadic would swallow inner arguments). `web` aliases `--profile web`; `plugin` forwards to pnpm in the profile directory and reconciles `freddie.profile.bundles` against installed state, and rewrites relative path specs against the invoking directory (pnpm runs with cwd = profile dir).
- The `web` profile re-execs Node once with `--expose-internals`: cordis-plugin-hmr throws without it and it can only be set at process launch.
- HMR watches an explicit list of `src/` directories, never the tree with a `node_modules` ignore glob: chokidar needed 30s+ (still not ready) walking `packages/` and `apps/` with the glob versus ~1.1s over the ~221 real `src/` dirs.
- Layer order: bundle layers, profile `cordis.patch.yml`, home `$FREDDIE_HOME/cordis.patch.yml` (outranks the per-profile layer), `--patch` overlays, telemetry switch. Any non-empty `FREDDIE_TELEMETRY_DISABLED` (even `0`/`false`) disables telemetry: privacy prefers off-by-mistake. The profile root config is rewritten every boot because Loader write-back can bake composed rows into it and duplicate bundle inserts.
- `FiberState` is mirrored at runtime because it is a cross-package const enum erased at compile time.
